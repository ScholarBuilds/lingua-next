# 处理网络访问：代理服务器、绕过规则与认证

代理设置决定部分网络请求是否先经过另一个服务再访问目标。它可能是家庭或工作环境中正常使用的配置，也可能让某些网站、App、内部地址或认证过程表现不同。这个页面不适合“为了学习英语而试着开关”；正确的学习目标是看懂每一项控制什么、识别哪些信息不能公开、在出现访问异常时能准确描述而不盲改。

> [!warning] 代理配置会改变网络路径
>
> 改动 HTTP、HTTPS、SOCKS、自动代理配置或绕过规则，可能影响浏览器、App、公司资源、登录认证和本机服务。除非你清楚配置来源、原始值和恢复方法，否则只读学习。不要把服务器地址、端口、认证信息或绕过列表写入讲义、聊天或词汇卡。

## 代理页先回答的五个问题

打开 Proxies 后，不要先看输入框里的值。先判断下面五件事，才能知道自己看到的是哪一种网络路径。

| 要问的问题 | 界面英文线索 | 它决定什么 |
| --- | --- | --- |
| 系统会自动寻找代理吗？ | `Auto proxy discovery` | 是否尝试发现网络提供的代理设置。 |
| 系统会自动载入配置吗？ | `Automatic proxy configuration` | 是否按某个自动配置规则决定代理。 |
| 哪一种请求经过代理？ | `Web proxy (HTTP)`, `Secure web proxy (HTTPS)`, `SOCKS proxy` | 不同协议或 App 流量的处理范围。 |
| 代理需要登录吗？ | `Your credentials may be sent unencrypted.` | 认证信息的传输风险和登录方式。 |
| 哪些地址不走代理？ | `Bypass proxy settings…`, `Exclude simple hostnames` | 例外规则和本地访问路径。 |

代理的核心不是“网络更快”或“网络更慢”，而是**请求先走哪里**。看到某个代理开关为 On，只能说明该类型的请求被配置为使用代理；是否能访问，还取决于代理服务是否可达、凭据是否有效、例外规则是否匹配以及目标资源是否允许访问。

| 完整英文 | 软件语境中文 | 它不表示什么 |
| --- | --- | --- |
| `Auto proxy discovery` | 自动发现代理。 | 任何网络都一定提供代理。 |
| `Automatic proxy configuration` | 自动代理配置。 | Wi-Fi 本身自动连接。 |
| `Web proxy (HTTP)` | Web 代理（HTTP）。 | 所有网络请求都会经过同一个设置。 |
| `Secure web proxy (HTTPS)` | 安全 Web 代理（HTTPS）。 | 当前网页内容一定端到端匿名。 |
| `SOCKS proxy` | SOCKS 代理。 | 它与 HTTP 代理完全相同。 |
| `Server` / `Port` | 服务器 / 端口。 | 可以根据网上示例随意填写。 |
| `Your credentials may be sent unencrypted.` | 你的凭据可能以未加密形式发送。 | 系统已经替你安全保存了所有密码。 |
| `Exclude simple hostnames` | 排除简单主机名。 | 关闭所有代理规则。 |
| `Bypass proxy settings for these hosts & domains:` | 对这些主机和域名绕过代理设置。 | 列表中的所有网站都被阻止。 |

`Bypass` 是本页最关键的动词之一。它不是“关闭代理”，而是让**匹配的目标**不经过代理。范围由后面的 `for these hosts & domains` 决定。理解范围是防止误操作的关键：一条绕过规则可能只影响内部服务，也可能影响某一类本地域名。

## 自动发现和自动配置不是同一个动作

两项都以 `Auto` 或 `Automatic` 开头，因此很容易混淆。它们都和“系统不必由你逐项填写”有关，但来源不同。

| 设置 | 英文中的核心词 | 阅读重点 | 启用前应确认什么 |
| --- | --- | --- | --- |
| `Auto proxy discovery` | discovery | 系统尝试发现网络提供的代理信息 | 当前网络是否明确要求此方式 |
| `Automatic proxy configuration` | configuration | 系统按自动配置规则处理代理 | 自动配置的来源是否可信、适用于哪个网络 |
| `Web proxy (HTTP)` | web proxy | HTTP 请求的代理路径 | 服务器和端口由谁提供 |
| `Secure web proxy (HTTPS)` | secure web proxy | HTTPS 请求的代理路径 | 对加密网站和认证是否有组织策略 |
| `SOCKS proxy` | SOCKS | 某类通用代理协议路径 | 具体 App 或网络服务是否要求它 |

从英文上看，`discovery` 偏向“发现信息”，`configuration` 偏向“采用一套配置”。不要因为两项都含 `proxy` 就同时打开；它们可能来自不同的网络管理机制。正确的提问是：

> `Does this network use proxy discovery, an automatic proxy configuration, or a manually configured proxy?`

这个问题明确了三种可能路径，也把决定权交给网络管理员或明确文档，而不是靠猜测。

## HTTP、HTTPS 和 SOCKS：先说范围，再说结果

HTTP、HTTPS、SOCKS 都是代理相关类型，但从软件英语角度，最重要的是知道页面将它们分开，意味着它们可能覆盖不同请求范围。遇到访问问题时，先描述“哪一种访问受到影响”，而不是笼统说“代理坏了”。

| 观察到的现象 | 可用英语 | 下一步应该确认 |
| --- | --- | --- |
| 网页访问受影响 | `Web traffic may be affected by the proxy settings.` | HTTP 和 HTTPS 代理是否启用、是否有正确来源。 |
| 某个 App 访问异常 | `This app may be using a different network path.` | App 是否使用系统代理、VPN 或自己的网络设置。 |
| 内部地址访问异常 | `The internal host may need to bypass the proxy.` | 是否有明确的绕过规则或组织说明。 |
| 登录页面异常 | `The proxy may require authentication or affect the sign-in flow.` | 凭据、认证方式和安全提示。 |
| 只是不确定影响范围 | `I need to check which traffic is configured to use the proxy.` | 不先关闭任意开关。 |

`may be affected` 和 `may be using` 是有意保留不确定性的表达。页面只能证明配置存在；是否是根因仍需通过现象、日志、网络管理员或受控测试确认。

## 绕过规则：例外比总规则更容易出错

当你看到 `Bypass proxy settings for these hosts & domains:`，应当把它读成“以下主机和域名走例外路径”。这条规则通常用来确保本地服务、内部资源或指定目标不被代理错误处理。它不是黑名单，也不是隐私保护开关。

| 表达片段 | 语法作用 | 正确理解 |
| --- | --- | --- |
| `Bypass` | 动作动词 | 绕开既有代理路径。 |
| `proxy settings` | 被绕开的对象 | 不是绕开整个互联网。 |
| `for these` | 范围限定 | 只对后面的目标生效。 |
| `hosts & domains` | 目标类型 | 可以是主机名或域名，不是任意文本。 |
| `Exclude simple hostnames` | 专门的例外开关 | 处理不带完整域名层级的简单主机名。 |

如果你不认识列表里的某项，不要删除它来“清理”。更安全的问法是：

> `Is this host or domain intentionally excluded from the proxy settings?`

它能让管理员确认该规则是否仍然必要，而不会让你在没有恢复记录的情况下修改网络路径。

## 凭据和未加密提示：风险文字必须逐字读

`Your credentials may be sent unencrypted.` 不是一般的“注意安全”。它明确指出：如果你在某种代理认证中输入凭据，传输方式可能缺少加密保护。这里的三个词都不能省略：

| 片段 | 含义 | 为什么重要 |
| --- | --- | --- |
| `credentials` | 用于认证的身份信息，例如用户名和密码 | 它比普通的 `password` 范围更广。 |
| `may be` | 可能会 | 系统提示潜在风险，不是断言已经泄露。 |
| `sent unencrypted` | 以未加密方式发送 | 描述的是传输方式，不是本机是否保存密码。 |

遇到这个提示时，正确行为是停止填写未知的认证信息，确认代理来源和组织要求。你可以说：

> `System Settings warns that proxy credentials may be sent unencrypted. I need to confirm the approved sign-in method before entering anything.`

这段话把界面警告、当前决策和下一步确认都写清楚了。

## 两个完整操作案例

### 案例一：只读识别当前代理结构

1. 打开 **System Settings → Wi-Fi → Details… → Proxies**。
2. 分别记录自动发现、自动配置、HTTP、HTTPS 和 SOCKS 的开关状态，只记 On 或 Off。
3. 找到 `Bypass proxy settings for these hosts & domains:`，解释它是例外规则而不是阻止规则。
4. 如果看见认证安全提示，读出 `may be sent unencrypted`，但不要输入任何凭据。
5. 不改服务器、端口或列表，选择返回或取消。
6. 用英语说明：`I reviewed the proxy types and bypass rules. I did not edit any server, port, credential, or exclusion.`

这句话把敏感字段逐类说明，适合告诉他人“我只检查过，没有修改”。

### 案例二：报告“网站打不开”而不直接关闭代理

1. 确认 Wi-Fi 页面显示连接状态。
2. 记录一个可观察现象，例如某个网页、内部服务或登录流程失败；不要在报告中附上敏感地址。
3. 打开 Proxies，只读确认当前有哪一类代理开关启用。
4. 不关闭代理，不删除绕过规则，不更改服务器和端口。
5. 用英语报告：`The Mac is connected to Wi-Fi, but a web service is not loading. I can see that proxy settings are configured, but I have not changed them. Could you confirm whether this service should bypass the proxy?`

这段话不会擅自认定代理就是根因，但给出了管理员可以继续判断的线索。

## 常见错误与恢复方式

| 错误 | 为什么风险高 | 正确替代 |
| --- | --- | --- |
| 访问异常就关闭全部代理 | 可能破坏公司、学校或本机服务的正常路径 | 先确认哪一种请求受影响、代理由谁配置 |
| 把绕过列表当作广告拦截名单 | 例外规则可能是内部资源依赖 | 逐条询问来源，不凭名称删除 |
| 填入网上找到的服务器和端口 | 来源未知，可能造成流量错误路由 | 只使用管理员或可信配置资料提供的值 |
| 看到未加密提示仍输入密码 | 可能增加凭据暴露风险 | 停止操作，确认批准的认证方式 |
| 用 Go Back 代替恢复 | 已确认的代理修改仍可能保留 | 回到同一页，恢复原开关和值，再次验证 |

## 代理、VPN 和 DNS 的排查顺序

代理、VPN 和 DNS 都可能影响“能不能访问一个名称或服务”，但它们位于不同层次。把它们全部叫作“网络设置”会让问题越查越乱。下面的顺序不是自动修复流程，而是帮助你在报告问题时先说明证据、再选择正确页面。

| 先确认什么 | 对应页面或状态 | 它排除或缩小什么 |
| --- | --- | --- |
| Mac 是否已连接 Wi-Fi | Wi-Fi 页的 `Connected` | 无线连接本身是否建立 |
| 是否存在代理路径 | Proxies 的启用状态和绕过规则 | 请求是否可能先交给代理服务 |
| 名称是否能被解析 | DNS 页面和实际名称现象 | 是否可能是名称解析范围或服务问题 |
| 是否有 VPN 连接或企业策略 | VPN 页、组织说明 | 请求是否通过另一条网络路径 |
| 是否只影响一个 App | App 的现象和系统代理范围 | 系统设置是否真是共同原因 |

可以用下面的英语把检查顺序说清楚：

> `I confirmed that Wi-Fi is connected. Next I checked whether a proxy is configured, then I reviewed the DNS page. I have not changed the proxy, VPN, or DNS settings.`

这段说明让对方知道你没有盲目修改，也没有混淆不同层次。若代理是组织强制配置的一部分，管理员可以直接告诉你不要继续改；若只有某个内网地址异常，对方也可以优先检查绕过规则。

## 凭据提示出现时的正确对话

如果代理页面或浏览器弹出认证窗口，首先区分它是要求“输入身份信息”，还是“系统解释存在安全风险”。前者可能需要组织账户；后者要求你先确认传输方式和来源。两种情况都不能因为想完成网络连接而随意输入密码。

| 你需要表达的意思 | 可用英语 | 作用 |
| --- | --- | --- |
| 系统正在要求代理认证 | `The proxy is asking for credentials.` | 说明发生的是认证，不是普通网络加载。 |
| 我不确定来源 | `I cannot confirm that this proxy configuration is approved.` | 保留安全边界。 |
| 页面提示未加密风险 | `The settings page warns that credentials may be sent unencrypted.` | 引用系统事实，不夸大为泄露。 |
| 我没有输入任何信息 | `I did not enter any credentials.` | 明确未产生认证操作。 |
| 需要管理员确认 | `Could you provide the approved proxy configuration and sign-in method?` | 请求可信来源，而不是索要别人的密码。 |

这类表达的价值在于能把“我看见了什么”和“我做了什么”分开。对于涉及凭据的任何系统页面，清楚地说 `I did not enter any credentials` 往往比长篇解释技术细节更能帮助对方判断风险。

## 修改以后怎样证明已恢复

如果在明确授权的维护中确实改过代理设置，恢复不能只靠“我把开关点回去了”。至少需要重新打开同一页面核对开关、服务器、端口和绕过列表，再验证受影响服务是否回到原行为。

```text
Before the change, I recorded the enabled proxy types.
After the test, I restored the previous settings.
I reopened the Proxies page and verified the original values.
I then checked whether the affected service behaved as before.
```

其中第二句描述恢复动作，第三句提供界面证据，第四句提供功能证据。三者缺一不可：页面值恢复不必然代表服务表现恢复，服务临时正常也不能证明配置没有遗漏。
