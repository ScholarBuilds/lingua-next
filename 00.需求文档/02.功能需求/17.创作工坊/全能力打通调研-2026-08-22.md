- **日期**：2026-08-22
- **对象**：lingua-next 工作树（`main@dafa9de` + 69 个未提交条目）· DeepSeek harness `b150a55`（= upstream HEAD，`dsh-v0.1.1-rc.2`）· Infinite-Canvas `VERSION 2026.08.04`

- **上一轮**：[插件化创作运行时重构方案-2026-08-21](./插件化创作运行时重构方案-2026-08-21.md)（自述阶段 A/B 完成、C/D 纵切）· [Infinite-Canvas能力差异调研-2026-08-21](./Infinite-Canvas能力差异调研-2026-08-21.md)（F001-F134）

> [!important] 本文是什么、不是什么
>
> 本文回答"怎么把所有能力打通成一套插件底座，让以后任何功能都能封装成工作流"。它**不是**上一轮方案的推翻，而是对它的代码级验收 + 补齐设计。上一轮落地的东西大部分是真的，但自述里有 9 处与代码不符（§2.8），其中 4 处会在用户面前直接表现为故障。

## 0. 一页结论

**现状**：插件化底座完成度约四成。可撤销注册 + 代际冻结 + 一次性 dispatch + 调用台账 + 持久 DAG/checkpoint + 追加事件表这六块是真代码、有测试（1219 pytest / 301 vitest / tsc / alembic 全绿）。但"一切皆插件"需要的三个前提**一个都没有**：

| 前提 | 现状 | 后果 |
| --- | --- | --- |
| 事件总线 / 中间件缝合点 | server 里 `grep waterfall\|middleware\|EventBus` 零命中 | 审批、重试、预算、超时、压缩……任何策略都只能改核心 if/elif |
| Provider 中立的消息与流式协议 | Chat Provider 被迫伪装 OpenAI SDK 对象（`model_runtime.py:367-401` 用 `SimpleNamespace`） | 接 Anthropic / Gemini 原生 / 本地模型都要复刻伪装层；chunk 解析在三处复制 |
| 工具 / 节点 / 工作流的单一 schema 源 | 输入合同三份手写副本已漂移；画布节点类型知识散在 9 个文件 | 新增一个工具：后端 3 文件 7 处 + 前端页面 + 画布节点 + Agent 手写，约 20 处改动 |

**四个直接影响体验的硬伤**（§2.8 有验证记录）：

1. `StudioTaskEvent.global_cursor` 非事务取号，SSE 按 `> cursor` 读 → 并发提交时事件永久漏掉；
2. `EventSource` 无 `onerror` 守护，一次 502 后整页 SSE 死亡且永不重建；
3. 画布产物落图只在浏览器做（服务端无 projector），关页面 = 等下次打开才落图；`FlowRun` 无事件行、不进 SSE 也不进任务中心；
4. `CapabilityBinding.fallback` 对 Chat/Image 路径完全不生效；LiteLLM 仍是运行前置条件（route 为空固定回落、绑定保存必须同步网关否则 502）。

**对 DeepSeek harness 的裁决**：不嵌入、不做 dsh 插件。它的 Python SDK 协议只有 `initialize / session.prompt / shutdown` 三个方法，无 cancel、无审批回调，单用户、loopback、JSONL 会话日志，覆盖不了 PostgreSQL 台账、arq 异步媒体任务、画布投影。**抄它的四条约定**（可撤销注册归属 owner、带 `next()` 的 waterfall 事件、Provider 中立的 Message/StreamChunk、工具固定管线 pre→guard→approval→around→post），按清单把约 20 个文件翻译成 ~2500 行 Python；前端按组件级搬 `ui-tool` / `ui-primitives` / `StatsLine`。工具箱额外输出一个 **MCP server**，作为 lingua 工具的公共出口——dsh、Claude Code、Codex 都能直接调用（§5.6）。

**对 Infinite-Canvas 的裁决**：上一轮文档自评 121 ✅ / 11 ◐ / 2 ○，代码复核后 ✅ 里至少 6 项实际不存在（按拓扑自动排列、拖入连线插入、叠放自动连线、连线合法性矩阵、分组连线合并、远端变更感知）。真实剩余缺口集中在 8 处（§4.2），其中导演时间线（Canvas2D 拖拽/播放头/波形）和更新回滚是两块最大的。IC 后端有 ~15 个函数群值得**整段搬**（§4.3），画布前端有 ~1500 行纯算法可直译（§4.4）。

**路线**（§6）：P0 提交基线 + 修四个硬伤（2-3 天）→ P1 内核三件套 EventBus / StreamChunk / ToolRuntime（约 2 周）→ P2 模型层收口（LiteLLM 降为普通 Provider、fallback、稳定错误码、retry、TokenUsage/cost）→ P3 统一事件流与服务端投影（subject 泛化事件表、pubsub、projector、cancel/lease）→ P4 工作流内核（子工作流/条件/map/暂停/模板、旧 pipeline 合并、脚本式运行时）→ P5 画布节点注册表 + IC 残余移植 + MCP 出口 + 插件包装配。P1 做完之前不要再往 `canvasStore.ts`（5945 行）和 `worker/tasks.py`（3283 行）里加功能。

### 2.5 工作流 / DAG

三个概念要分清：(a) `StudioWorkflow` = ComfyUI/RunningHub 的外部定义，是 `workflow.run` 一个 operation 的 Provider；(b) `StudioFlow/StudioFlowRun` = 自有持久 DAG；(c) 画布级联/成套 = 浏览器编译成 inline run。

**已成立**：定义校验严格（重复 id / 悬空边 / 自环 / 拓扑环 / 未连线引用）；节点级 checkpoint + 按 `batch_id` 收养子任务；续跑只把 failed/cancelled 回 pending；`$artifacts` 把异构结果归一为 image/video/audio/file 引用；API 先持久化再入队。

**它是"静态 DAG 执行器"，不是"可封装工作流"的承载层**：

| 严重度 | 问题 | 证据 |
| --- | --- | --- |
| 高 | 无行锁、tick 可重叠：延迟 tick 无 `job_id`，启动恢复另用 `recover-studio-flow:{id}`，两个 `advance` 并发各自建重复 `StudioTask` | `tasks.py:2917`；`worker/main.py:182-185`；`studio_flows.py:797-806` 无 `with_for_update` |
| 高 | cancel 不传播：只改 run 状态，子任务继续跑；系统根本没有 `StudioTask` 取消端点 | `routers/studio_flows.py:178-194`；`studio_tasks.py` 仅 retry |
| 高 | 产物投影只在浏览器：服务端从不写 `StudioCanvas.nodes`；关浏览器产物停在 `StudioTask`，下次打开且受 50/500 候选上限 | `canvasStore.ts:5414-5434, 5557-5590`；`grep StudioCanvas server/worker` 零写入 |
| 中 | 首个节点失败即整 run failed；无每节点重试 / 退避 / `on_failure` 策略 | `studio_flows.py:841-854` |
| 中 | 无 run / 节点超时，`heartbeat_at` 只写不读 | `studio_flows.py:321`；`workflow_execution.py:39` 唯一超时是 Provider 轮询 3600s |

### 5.3 统一事件流与投影（"刷新不丢"的正解）

```text
写侧（同事务）                    推送                       读侧
transition()/checkpoint ──► domain_event ──► NOTIFY/pubsub ──► /api/events 单路复用流
                           (subject_type,                       frame: subscribed{lastCursor}
                            subject_id, seq,                    frame: event{seq, whole snapshot}
                            global_cursor)                      frame: snapshot{FlowRun/PipelineRun 过渡}
                                 │
                                 ▼
                     服务端 projector（worker 内）
                     task 终态 → 按 source_context.canvas_id/node_id
                     写 StudioCanvas.nodes[].items，bump version，发 canvas.updated
```

| 设计点 | 做法 | 替代的现状 |
| --- | --- | --- |
| 事件表泛化 | `StudioTaskEvent` → `domain_event(subject_type ∈ task/flow_run/pipeline_run/canvas, subject_id, seq, global_cursor, type, data)` | `FlowRun` 无事件、`PipelineRun` 另一套 SSE |
| `global_cursor` 安全 | 取号放事务内 advisory lock，或读侧按 `(created_at − 2s, cursor)` 安全窗回扫并以 `(subject, seq)` 去重 | 非事务序列 + `> cursor` 漏事件 |
| 推送 | 事务提交后 `pg_notify('domain_event', cursor)`（或复用 arq 的 Redis pubsub）唤醒流，再按 cursor 补历史 | 每连接每秒查库 |
| 单连接多路复用 | `/api/events` 一条流承载全部 subject；连接建立先发 `subscribed{lastCursor}`；无事件表的 subject 先用 whole-snapshot 帧过渡 | `/studio/tasks/events/stream` + `/pipeline/stream` 两条 |
| whole-value payload | 事件携带整条任务快照，前端按 `(subject_id, seq)` higher-wins 直接折叠，不再 GET `/tasks/{id}` | N+1 回查 + `syncingCanvasTasks` 互斥 |
| 重连 | `TaskStreamController`：generation 计数、`onerror → abort → backoff → 重建`、`onConnected` 重拉基线 | 无 `onerror` |
| 服务端 projector | worker 终态后写画布节点 items + bump version + 发 `canvas.updated`；浏览器降级为只读订阅 + 409 合并 | 只有浏览器落图 |
| 投影单元 | `ProjectionDefinition{init, apply(state, event), view, stateVersion}` 纯函数，Python/TS 同构；画布打开先读 checkpoint 再回放 cursor 之后事件 | `recover*/track*/land*` 四路手写 |
| 租约与取消 | 执行器每 30s 写 `heartbeat_at`；cron 扫过期置 recovering/failed；`POST /tasks/{id}/cancel` 写 `cancel_requested` + 事件，执行器轮询点协作取消，`arq allow_abort_jobs=True`；flow cancel 级联 active 子任务 | 无取消、无租约 |
| 全局任务中心 | `RunningDock` 与 `TaskCenter` 同时消费 `/api/events`；第二步 `PipelineRun` 也写进泛化事件表 | 两套 UI 两套流 |

### 5.6 MCP 出口与 dsh 的位置
