# 视频与字幕学习 v2

> [!info] v2 修订说明
>
> v1（基础管线：下载/转写/双语字幕/逐句精听）已于 M2 交付。v2 按 scholar 提供的参考产品（TEco Lab 形态截图）深挖扩展：目标是**功能超集**——参考产品有的全要有，再叠加本项目独有的全局打通能力（FSRS 生词闭环、AI 陪读、分析缓存、配置中心）。交付门槛：10+ 条精选 YouTube 英语学习视频完成全管线加工后随功能一起交付。

## 1. 页面地图（三页打通）

```
视频库 /video ──打开──▶ 学习页 /video/:id ──模式──▶ 八种学习模式（同页切换）
    │                        │
    ├─ 批量导入面板            ├─ 生词 → FSRS 复习（出处带时间戳回跳）
    ├─ 筛选/搜索/排序          ├─ 句子收藏 → 收藏体系
    └─ 继续学习横幅            └─ AI 陪读（持本视频字幕全文上下文）+ 看板娘
```

## 2. 视频库页（对标参考图 1，超越点标注 ▲）

### 2.1 视频卡片
- FR-01 卡片信息：封面（时长角标+作者名）、标题（AI 中文标题或原题）、**AI 中文摘要**（2-3 句剧情/内容概述）、**难度星级 1-5**（按字幕词汇 CEFR 分布+语速算出，展示星标）、**口音标签**（美/英/澳/加/印/非母语者，AI 判定）、**主题标签**（生活/旅行/播客/科技/美食…AI 生成 1-3 个）、词汇量（去重词数）、字幕句数、导入日期。
- FR-02 ▲学习状态叠加：进度环（已学句子占比）、"继续学习"角标、收藏书签角标；已学完卡片降透明度。
- FR-03 ▲卡片悬停快捷操作：继续学习/收藏/重新加工/删除。

### 2.2 筛选与组织
- FR-04 筛选栏：难度（星级多选）、口音、主题标签、时长区间（<3min/3-10/10-30/>30）、学习状态（未开始/学习中/已学完/已收藏）；搜索（标题/作者/字幕全文 FTS）；排序（最新/难度/时长/进度）。
- FR-05 顶部"继续学习"横幅（最近学习视频+进度+一键回到上次句子）。
- FR-06 ▲精选频道源：内置一批优质英语学习频道清单（生活 vlog/慢速英语/播客/访谈），支持"从频道拉取最新 N 条"批量导入；粘贴多 URL 批量导入（逐行）。
- FR-07 处理中卡片实时进度（下载/转写/AI 加工分阶段）；失败卡片可重试可查因。

## 3. 学习页（对标参考图 2，八模式）

### 3.1 布局与播放器
- FR-08 左视频右字幕两栏（栏宽可拖拽）；**隐藏视频模式**（纯听力，视频区折叠为音频波形条）▲；全屏；画中画 ▲。
- FR-09 播放控制条：倍速（0.5-2.0 细档）、上一句/播放/下一句、**A 点标记 + A-B 循环**、单句循环、**句间间隔**（逐句暂停 0-5s 可调）、**单句暂停开关**、音标开关（字幕句下逐词 IPA 行）。
- FR-10 ▲视频内字幕：双语叠加、词可点（已有）+ **词级卡拉OK高亮**（whisperX 词级时间戳，当前词随语音高亮）。

### 3.2 字幕列表（右栏）
- FR-11 句卡：英文（**关键词组彩色高亮**——AI 预提取的 collocations/短语动词，不同类型不同色）+ 中文 + 序号/时间戳；当前句跟随高亮滚动（已有）。
- FR-12 每句操作行：复制、**收藏句子**（入收藏体系）、**编辑字幕**（就地改错，改后该句分析缓存失效）、**跟读录音**（录音→与原句波形对比回放→AI 发音反馈[基于 whisper 转写比对，标出漏读/错读词]）、单句播放。
- FR-13 ▲句级学习标记：听懂了 ✓（计入进度）；难句旗标（进复习清单）。
- FR-14 点词=学习卡（已有全套），生词点线标记（已有）；**收藏生词带视频出处**（video_id+cue+时间戳，复习卡回跳该秒，M5 已建字段）。

### 3.3 八种学习模式（seg 切换，同页无跳转）
| 模式 | 行为 |
| --- | --- |
| 双语 | 默认形态（视频+双语字幕列表） |
| 英语 / 中文 | 字幕列表只显示单语（视频内字幕同步切换） |
| **听写** | 逐句播放→输入框打字→逐词批改（对绿错红漏灰）→重听/看答案/下一句；正确率统计入进度 |
| **挖空** | 字幕关键词挖空（难度自适应：优先词组/生词），点击候选或键入填空；即时判定 |
| **阅读** | 纯文本精读形态：字幕拼成段落文章，接入阅读器全套（点词/句面板/双语对照/批注） |
| **中译英** | 显示中文→用户口说（录音转写）或键入英文→AI 对比参考句评分与建议 |
| **词卡** | 本视频词汇卡片流（AI 提取的重点词+词组，含出处句），可批量入生词本 |
- FR-15 各模式进度独立记忆；模式间切换保持当前句位置。

### 3.4 全局打通 ▲（参考产品没有的）
- FR-16 AI 陪读：学习页可唤起（含看板娘），AI 持本视频全部字幕上下文，可问"刚才那句的梗/语法/文化背景"；点击字幕句 AI 感知（复用 ChatTextQuery 链路）。
- FR-17 视频生词自动进 FSRS 复习，复习卡"视频名·时间点"出处一键回跳播放。

## 4. 内容加工管线（AI enrichment）

- FR-18 加工任务链（下载→转写后追加）：AI 摘要+中文标题 → 难度评级（CEFR 词表分布+语速 wpm）→ 口音判定 → 主题标签 → **词组/搭配提取**（每句标注 collocations 区间+释义，落库供高亮）→ 重点词汇表（词卡模式数据源）。全部走 LLM 别名 `summary-long`/`explain-standard`，结果按 ADR-006 缓存。
- FR-19 词级时间戳：whisperX 强制对齐（配置开关，默认开）供卡拉OK高亮；官方字幕无词级则按字符比例插值近似 ▲。
- FR-20 加工可重跑（单项重跑：仅摘要/仅词组），版本化。

## 5. YouTube 接入与凭证（配置中心新增）

- FR-21 配置中心"视频源"分类：**YouTube 凭证**三种方式任选——① cookies.txt 粘贴（浏览器插件 Get cookies.txt 导出，存凭据库加密）② `cookies-from-browser`（选择本机浏览器 chrome/safari/edge，服务端本机部署时可用）③ 不配置（受 bot 校验限制）；代理地址配置（已有 env 迁入凭据库）；下载画质偏好（1080/720/最高）。
- FR-22 凭证失效检测：下载失败为 bot 校验/登录墙时状态标注"凭证失效"并引导更新。
- BR：cookies 属敏感凭据，Fernet 加密入库、掩码展示、不入日志。

## 6. 业务规则（v1 保留 + v2 增补）

# v3 修订：句层重组与交互对齐（2026-08-17，真实使用反馈驱动）

> [!info] v3 触发背景
>
> scholar 真实使用中提出两点：① 词组（短语动词/搭配/习语）悬浮时高亮的应是整个词组而非单词；② 右栏字幕句是否该组装成完整句。排查后发现②底下压着更根本的字幕数据质量问题，一并纳入本轮。

## 9. ASR 管线升级（v3 新增，选型与实测见 [ADR-007](../../../01.项目文档/02.架构/ADR/ADR-007-视频字幕ASR管线选型.md)）

- FR-35 转写模型由 `small` 升为 `large-v3`，`condition_on_previous_text` 保持默认 True（关闭虽快 40% 但丢 7.7% 词、改 49 词，实测否决）。
- FR-36 转写后追加**标点恢复**：按 segment 边界分块 ≤1600 字符、并发 6，走 LLM 别名 `explain-standard`，system prompt 严格约束"同词同序、只加标点与大小写"。
- FR-37 标点恢复必须过**词序列一致性校验**：归一化（小写、去首尾标点）后逐词比对，不一致则该块回退原文并记警告，绝不落库未校验文本。
- FR-38 词级时间戳由 whisper DTW 改为 **CTC 强制对齐**（ctc-forced-aligner / MMS-300M），供卡拉OK高亮。
- BR-13 标点恢复与强制对齐均为可重跑的独立阶段，失败不阻断已有产物（转写结果仍可用，降级为 DTW 时间戳 + 原始标点）。

**实测基线**（5 号视频 14.4 分钟，全库最坏案例）：

| 阶段 | 耗时 | 产出变化 |
| --- | --- | --- |
| large-v3 转写 | 830s（RTF 0.96） | 88 段 8078 字符 |
| LLM 标点恢复 | 9s（6 块并发） | 句末标点 19 → 96 个，校验 6/6 通过 |
| CTC 强制对齐 | 186s（RTF 0.215） | 词跨度中位 0.220s → 0.120s |
| pysbd 分语法句 | — | 18 句（最长 3866 字符）→ 92 句（最长 316） |
| 学习句二次切分 | — | 174 句，中位 46 字符 / 2s，仅 3.4% 超限 |

全库 123 分钟音频回填约 2.4 小时，一次性。

## 10. 字幕数据模型：三级结构（v3 新增）

### 10.1 问题实证

当前 cue（字幕行）既是时间轴单位又是学习单位，但 cue 由 ASR/平台按时间切分，与句子边界无关。15 号视频（伦敦一日游）whisper 轨 71 条 cue 实测：

| 指标 | 数值 |
| --- | --- |
| 不以句末标点收尾（断在半句） | 52 条（73%） |
| 以小写字母开头（承接上条尾巴） | 46 条（65%） |

全库 1713 条 cue 重组后为 1329 句，平均 1.29 条 cue 合成 1 句；13 号视频 51 句中 28 句（55%）跨 cue。听写、跟读、中译英、句收藏全部建立在半句之上。

### 10.2 三级模型

```
cue（字幕行，原样保留）      时间轴单位：卡拉OK词级高亮、进度条跳转、A-B 循环
  └ sentence（语法句）        语境单位：翻译送审语境、AI 陪读引用、词组区间定位
      └ study_unit（学习句）  练习单位：听写/跟读/中译英/句收藏/已学标记
```

- FR-23 语法句由 cue 文本流拼接后经 pysbd 分句得到（复用 `domain/segmentation.py`，文章模块同一实现）；句起止毫秒 = 首词 start / 末词 end，取自词级时间戳，非按字符比例插值。
- FR-24 学习句切分：语法句 ≤7 秒且 ≤84 字符时直接作为学习句；超出则在句内按优先级切分——句中标点（`, ; : —`）> 词间停顿 ≥300ms > 从属连词（and/but/because/that/which…）。每个学习句记录所属语法句 id。
- FR-25 词组区间定位改在语法句层进行（当前在 cue 层，跨 cue 的词组如被切断的 `going back to` 定位不到）。

**阈值依据**：Netflix Timed Text Style Guide —— 单条字幕最长 7 秒、每行 42 字符、最多 2 行（故 84 字符）、阅读速度上限 20 CPS。647 句实测样本（7 条已有标点的视频）中时长 >7s 占 9.6%、字符 >84 占 14.2%、阅读速度中位 17.0 CPS / P90 26.3 CPS，即约一成句子需要二次切分。

**BR-07** 翻译按语法句送 LLM（保完整语境与译文质量），学习句携带所属语法句作为 context；学习句不单独送翻译。

## 11. 词组交互对齐（v3 新增）

### 11.1 问题实证

| 位置 | 悬浮高亮 | 点击行为 |
| --- | --- | --- |
| 右栏字幕列表 `CueText` | 单词变底色 | 整个词组查 phrase ✅ |
| 视频内叠加字幕 `KaraokeCaption` | 单词变底色 | 单词查词典 ❌ |

叠加字幕已算出每个词的 `phraseIdx` 词组归属，但只用于渲染下方彩色提示行，未接管点击。

- FR-26 词组区间整体悬浮高亮：鼠标进入区间内任一词，整个词组区间统一加深；区间内单词不再各自响应 hover。右栏列表与视频内叠加字幕行为一致。
- FR-27 视频内叠加字幕的词组区间接管点击：点击走 phrase 分析（与右栏一致），区间外的词照常点词开卡。
- BR-08 词组区间内的词不各自响应点击——整个词组是一个语义单元；词组释义卡内的英文仍可逐词点查（递归压栈）。

- FR-28 识别上述非语音标记（方括号与全角/半角圆括号三类都要覆盖）：不翻译、不计入句数与进度分母、不可点读、听写与跟读自动跳过、视觉弱化显示。
- BR-09 标记判定在入库阶段完成并落 `is_noise` 标志，不在前端做正则兜底。

## 13. 中文译文来源统一（v3 新增）

### 13.1 问题实证

14 条精选视频的字幕轨盘点：

| 情况 | 视频数 | 双语可用性 |
| --- | --- | --- |
| whisper/en + translation/zh，cue 数完全相同 | 4 | ✅ 一句一译，完美对齐 |
| 有 YouTube auto/zh 但无 translation 轨 | 8 | ❌ 切分口径不同，严重错配 |
| 完全无中文轨 | 2 | ❌ 双语模式空白 |

15 号视频英文 71 条 / 中文 190 条，前端 `zhOfCue` 取英文句中点落入的那条中文全文，于是半句译文（`我要回英国了，你要跟`）与噪声标记（`[音乐]`）直接上屏，而页面底部仍标注"whisper 词级对齐"。

- FR-29 中文一律由 `translate_track` 基于 whisper 轨自建，与英文语法句一一对应；YouTube auto/zh 轨不参与双语渲染。
- FR-30 灌库管线中 `translate_track` 为必经步骤，缺失时视频状态不得置 ready。
- BR-10 YouTube auto/en 轨全小写无标点（奥巴马演讲 276 条 cue 合成 1 句 9609 字符），不可用于分句，英文源只取 whisper 轨。

## 14. 学习状态服务端持久化（v3 新增）

- FR-31 句收藏、已学 ✓、难句旗标、字幕人工修正从 localStorage 迁至服务端，换设备可续，为未来多用户铺路。
- FR-32 各模式进度（听写/挖空/中译英正确率与位置）同步服务端。
- BR-11 开发期不保留 localStorage 兼容读取，旧数据直接丢弃。

## 15. 跟读与陪读补全（v3 新增）

- FR-33 跟读录音经服务端 whisper 转写后与原句做词序列 diff，标注漏读/错读/多读词（当前仅波形包络对比）。
- FR-34 AI 陪读支持视频上下文：realtime session 接受 `video_id`，开场注入全片字幕与 AI 摘要，点击字幕句经 ChatTextQuery(501) 注入当前句，与文章陪读同口径。
- BR-12 录音仍只本地暂存与回放，用户明确保存才落库（BR-04 不变）；转写为一次性调用，不留存音频。

# v4 修订：订阅发现与管线补漏（2026-08-18，真实使用反馈驱动）

> [!info] v4 触发背景
>
> scholar 使用中提出五点：词卡/词组卡朗读热区太小、中文字幕要手动生成、
> 18 号视频字幕黏成一坨、希望像 Obsidian RSS Dashboard 那样订阅 YouTube 频道。
> 其中「字幕黏连」查证为 v3 管线自身的缺陷（标点恢复失败只回退不重试），
> 「手动生成字幕」是 FR-30 写了但实现漏了，一并修。

## 16. 标点恢复兜底（修 v3 缺陷）

### 16.1 问题实证

18 号视频（慢速英语聊韩国旅行）轨 meta：`{"chunks": 5, "passed": 3, "restored": true}`
——5 块只过 3 块，未过校验的 2 块按设计回退原文，于是留下 1645 字符无标点长段；
pysbd 切不动，只能靠停顿与连词硬切成 38 个学习句，即截图里黏连那段。

根因是 v3 实现只做「校验失败 → 回退原文」，没有重试。而 LLM 输出有随机性，
同一块重试或换更小的块很可能就通过了。

### 16.2 需求

- FR-39 词序列校验失败时同块重试一次（新请求，不复用上次输出）。
- FR-40 重试仍失败则把该块二分为更小块分别恢复，递归至最小块（约 400 字符）；
  块越小越容易保持词序列一致。
- FR-41 最终仍失败的块回退原文并落 meta（`punctuation.failed_chunks`），
  校验脚本报出来，不静默留黏连段。
- BR-14 任何情况下都不落未过校验的文本——宁可无标点，不可错词（BR-04 不伪造）。

## 17. 中文字幕自动化（补 FR-30 实现）

- FR-42 灌库管线在句层建成后自动入队 `translate_track`，不需人工点「生成中文字幕」。
- FR-43 视频状态在译文完成后才置 `ready`；翻译期间状态为 `translating` 并显示进度。
- BR-15 翻译失败不阻断视频可用性：状态置 `ready` 但标注「译文缺失，可重试」，
  学习页双语模式给出重试入口（BR-06 不静默降级）。

## 18. YouTube 订阅与发现（v4 新增）

### 18.1 方案选型（实测）

| 方案 | 实测结果 | 采纳 |

# v5 修订：预览可靠化与 Data API 分工（2026-08-18）

> [!info] v5 触发背景
>
> v4 的发现页上线后，scholar 反馈：内置频道有三个不存在（已修，id 硬编码之误）、
> 预览打不开（"Sign in to confirm you're not a bot"）、弹窗样式散乱。
> 排查后确认预览失败是**出口 IP 信誉**问题，不是配置能解决的。

## 21. 预览：本地片段为主，iframe 为辅

### 21.1 问题实证

| 尝试 | 结果 |
| --- | --- |
| iframe + `youtube-nocookie` | 部分视频被 bot 校验拦（同一批里 BBC 能嵌、Rachel's 被拦） |
| yt-dlp 换 `player_client`（web_safari / android / ios / tv） | 四种全部被拦 |
| 关掉代理直连 | 同样被拦 |
| **带凭证下载 360p** | ✅ 31 秒视频 **11.5s / 429KB** |

出口 IP 为 `AS2914 NTT America`（机房段），YouTube 对机房 IP 的 bot 校验最严。
这不是凭证或参数问题：iframe 由浏览器直连 YouTube，服务端 cookies 传不进去（同源策略），
换 player_client、换 Data API 都绕不过——**Data API 只提供元数据，不提供播放**。

### 21.2 需求

- FR-53 点预览时服务端带凭证下载片段（前 60 秒、≤360p），前端用 `<video>` 本地播放：
  可拖动、可反复看，不受 bot 校验影响。
- FR-54 片段按 `video_key` 缓存复用，入库时可直接升级为完整下载，不重复拉。
- FR-55 iframe 保留为快通道：先尝试内嵌，失败或用户主动点「加载可播片段」再走 FR-53。
- BR-18 预览片段计入磁盘管理：单条 ≤5MB，总量超限时按最近未访问淘汰。

## 22. YouTube Data API v3 接入（与 yt-dlp 分工）

### 22.1 分工依据

| | yt-dlp | Data API v3 |
| --- | --- | --- |
| 元数据速度 | 3-8 秒/条 | **毫秒级** |
| 受 bot 校验 | 是（需凭证） | **否**（key 鉴权） |
| 配额 | 无 | `videos.list` 1 unit / 最多 50 条，日配额 1 万 units |
| 字幕语言明细 | ✅ 逐语言列出 | ❌ 仅 `caption: true/false` |
| 下载能力 | ✅ | ❌ |

故：**Data API 管快速批量元数据，yt-dlp 管字幕语言探测与下载**，各取所长。

### 22.2 需求

## 26. v5 实施修正（2026-08-18 实测）

三处实现细节与设计时的设想不同，记在这里免得后来者重走：

**片段下载不能用 yt-dlp 的 `download_ranges`。** 它把 ffmpeg 当下载器直连
googlevideo，本机实测稳定 `ffmpeg exit 187/196`（TLS 连接超时），而 yt-dlp 自己的
HTTP 栈拉同一条 URL 秒开。改为三步：yt-dlp 取直链 → 用 yt-dlp 的 `urlopen` 发
`Range: bytes=0-N` 只拉够 60 秒的字节（N 由码率反推）→ ffmpeg 纯本地裁切不碰网络。
实测 BBC 6 分钟片：extract 6.2s + 拉流 3.5s + 裁切 0.1s，产物 1.2MB / 精确 60.0 秒。

**Shorts 常常 ≤360p 只有 HLS 流。** 对 `m3u8_native` 格式发 Range 请求拿到的是清单
文本，ffmpeg 报 `Not detecting m3u8/hls with non standard extension`。故格式选择器加
`[protocol^=http]` 把 HLS 排除在快路径外，另开一条兜底：≤360 秒的短片交给 yt-dlp
整片下载（它的分片下载器好使，59 秒 Short 实测 12.3s / 1MB）再本地裁切；更长的直接
报错引导去 YouTube 看，不为 60 秒预览拉全片。

**字幕 URL 也可能是 HLS 清单。** 部分 player_client 下 yt-dlp 标 `ext=vtt` 的条目
实际返回 `#EXTM3U`，真正的字幕在清单里的分段 URL（实测 BBC 频道全部走这条路径）。
解析一律按内容嗅探而非扩展名，遇清单就跟进分段再拼接。

### 实测结果

| 验收点 | 实测 |
| --- | --- |
| AC-15 | 机房 IP 下预览正常播放；HLS-only 的竖屏 Short 也可播（16:9 内 contain 留边不裁切） |
| AC-16 | `POST /feed/refresh-meta` 回填 **75 条 / 1.8 秒**（2 次请求 = 2 units），卡片直出时长与字幕标志；同样数据走 yt-dlp 需 75 × 6s ≈ 7.5 分钟 |
| AC-17 | 无 key 时详情端点回退 yt-dlp 逐条探；配额耗尽（403 quotaExceeded）单独分型并回退，不静默失败 |
| AC-18 | 候选详情首次 10.4 秒（含下字幕 + 词频统计），二次 24ms 命中已落库结果；BBC 6 分钟片测得 wpm 154.7 / 难度 4 星 |
| AC-19 | 1280×800 与 1920×1080 下播放区宽高比均为 **1.777**（严格 16:9），页面无横向溢出 |

> 播放区一开始写 `width:100%` + `aspect-ratio:16/9`，在 flex 列容器里被压成 2.21:1。
> 改为由可用高度反推宽度（`width: min(100%, calc(56vh * 16 / 9))` + `flex: 0 0 auto`）才严格成立。

# v6 修订：管线可观测性与节点级重跑（2026-08-18，故障驱动）

> [!danger] v6 触发背景
>
> v5 上线后新入库的 21/22/23 三条视频字幕列表全空。排查发现 **arq worker 是
> 8-17 18:19 起的进程，跑的是 ADR-007 三级管线并入 `ingest_video` 之前的代码**：
> cue 正常写入（12/26/9 条），但句层从未构建（`sent=0`）、轨 meta 为空、中文轨缺失。
> 视频状态一路 `ready 100%`，故障静默了六个小时，最后靠手工查 SQL 才发现。
>
> 结论不是"重启 worker"这么简单——**管线没有任何节点级可观测性**，产出静默降级
> 而状态机毫无察觉。v6 按"让这类故障不可能再静默"来设计。

## 27. 问题分析

| 现状 | 后果 |
| --- | --- |
| `video.status` 只有 6 个粗粒度值 | 只知道"到哪个大阶段"，不知道每步做了什么 |
| `video.progress` 是单一 0-100 数字 | 无法区分是慢还是卡住，无法定位是哪一步 |
| 节点信息只在 worker 日志里 | 日志滚掉就没了，产品里查不到 |
| `ready` 判定只看流程跑完 | 句层为空、译文缺失照样判 ready（本次故障的直接放行者） |
| 校验只有离线脚本 `verify_video_pipeline.py` | 不在产品里，要人记得手动跑 |
| 无版本指纹 | 代码更新后旧产物无从识别，本次故障的根本盲区 |
| 重跑只有整条 `retry` 与 enrich 的 `only=` | 想只重切句层，得整条重下重转 |

## 28. 业内调研与选型

| 来源 | 采纳 | 不采纳的部分与原因 |
| --- | --- | --- |
| **Dagster** | Run/Step 数据模型；从失败处重跑 + 步骤子集选择；每步独立 logs/metadata；**`code_version` 陈旧标记** | 不引入运行时——要独立 server 与独立 DB，个人项目 12 节点线性管线用不上 |
| **Prefect** | 反面教材：至今**不能从 UI 重跑单个失败 task**（[discussion #15829](https://github.com/PrefectHQ/prefect/discussions/15829)），只能整流程重跑 | 不用 |
| **Airflow** | `TaskInstance.try_number`、Gantt 时间轴 | 同样不引入运行时 |
| **OpenTelemetry** | span 语义作字段命名（trace/status/attributes），将来接 APM 不必改模型 | 不上 collector |
| **Dagster [issue #32052](https://github.com/dagster-io/dagster/issues/32052)** | "重跑时改运行配置"是公认缺口 → 我们直接做进去 | — |
| **React Flow / dagre**（MIT） | DAG 渲染与自动布局 | — |
| **LLM-as-judge 无参考评测** | 无金标准时用 LLM 裁判 + 确定性指标组合 | 不做 WER：没有参考文本 |

**决策：不引入编排器，抄它们的数据模型与交互语义**（详见 [ADR-008](../../../01.项目文档/02.架构/ADR/ADR-008-管线可观测性与节点级重跑.md)）。
arq 保持不变，只负责派活；运行记录由领域层落库——这正是 arq 官方推荐的
`on_job_start` / `after_job_end` + 自建表模式。

> 项目里已有这个模式的雏形：`POST /videos/{id}/enrich?only=phrases` 已能单步重跑
> AI 加工四步之一。v6 是把它从"enrich 四步"推广到"全链路十二节点"。

## 29. 管线运行记录（FR-64~66）

- FR-64 十三个节点定名并全程落库，`enrich.*` 四步为并行分叉：
  `download → probe → subtitles_fetch → transcribe → punctuate → align → sentences →
   translate → {enrich.summary, enrich.difficulty, enrich.phrases, enrich.vocab} → verify`
- FR-65 每步记 `metrics`（量化产出）与 `config`（实际用的模型与参数），具体到能判断好坏：

| 节点 | metrics 至少包含 |
| --- | --- |
| download | 文件大小、实际清晰度、yt-dlp 版本 |
| transcribe | 模型名、RTF、段数、词数、检出语言 |
| punctuate | 块数·通过·失败、是否自适应跳过、LLM 别名与模型 |
| align | engine(ctc\|none)、重定时 cue 数、最大偏移 |
| sentences | 语法句·学习句·超限·噪声数、最长句字符数 |
| translate | 句数、缓存命中、新增调用、引擎 |
| enrich.* | 各步产出计数 |

- FR-66 **版本指纹**：每步记 `code_version`（管线常量，改管线即改）。当前版本与产物版本
  不一致时标 **`陈旧`**（抄 Dagster staleness），视频库可筛"用旧管线跑的"并批量重跑。
  本次故障在这条规则下会立刻显形，而不是六小时后靠查 SQL。
- BR-22 记录只增不改：重跑产生新 `pipeline_run` 并以 `parent_run_id` 指向原 run，
  历次运行可对比（换模型前后超限句数变化一目了然）。

## 30. 进度中心（FR-67~70）

- FR-67 顶栏常驻入口，有任务时显示计数徽标；抽屉列出运行中/排队中/最近完成/失败，
  跨页面可见（v5 的 `/feed/queue` 只在发现页角落）。
- FR-68 进度走 **SSE 推送**替掉 3 秒轮询，复用服务端已有的 `_sse_response` 基建；
  空闲零请求，节点切换即时可见。

## 35. v6 实施修正（2026-08-18 实测）

**`single` 范围不能对所有节点开放。** 设计时以为"只跑这一步、下游沿用旧产物"处处成立，
实测踩了：对 `sentences` 用 `single` 重跑后，视频 22/23 的译文与词组全没了——因为译文
（`sentence.text_zh`）与词组区间（`sentence.phrases`）就挂在句记录上，重建句层等于连它们
一起删。故给节点加 `single_ok` 标记：`transcribe / punctuate / align / sentences /
translate` 一律只能连着下游跑，服务端直接 400 拒绝并说明原因，前端也不再渲染这个选项；
`enrich.*` 与 `verify` 产物独立，才允许单跑。

**auto 轨的清理要放在句层重建里。** 原本只在"写入新 whisper 轨"时顺手删 auto 轨，
于是老数据重跑句层时清不掉，体检报的 `fix_step` 点了没用。改为 `sentences` 节点无论是否
重写轨都清一次，报出来的修复动作才真的能修。

**SSE 要显式检测断连。** 外壳的进度入口与追踪页各订阅一次，最初各开一条 EventSource，
服务端就多一路每秒查库；且浏览器关页后生成器还在跑。改为前端全局共享一条连接
（最后一个订阅者退订才关），服务端每轮 `request.is_disconnected()` 检查。

## 50. v7 实施修正（2026-08-18 实测）

**修复代理引用的常是"它自己改写过的文本"。** 代理先用 edit_sentence 给长句补了标点，
随后拆分时引用带新标点的版本，与库中原文逐字符对不上，`split_sentence` 连续找不到
切点。修法：`_locate` 先精确匹配，不中则按**归一化词序列**（小写、去标点）匹配前
3-5 个词定位——对代理和人的"凭记忆引用"都鲁棒。

**占位序号是一类缺陷，不是一个缺陷。** `(track_id, ordinal)` 唯一约束在 autoflush
即生效，三处"先占位后重排"全踩了同一坑：学习句重建用 `ordinal=0`、拆句的新句沿用
原句序号、重排中途正负交换。统一修法：占位一律用**全轨唯一的负数**
（`-(row_id*100+idx)`），`_renumber` 两段式（先负后正）落正式序号。

**`resegment_sentence` 是黏连长句的标准修法。** 逐次指定切点让代理拆句，引用文本
稍有出入就失败；改成"先 edit_sentence 把标点补进原文，再一次 resegment 按标点
切开（pysbd，与管线分句同引擎）"，832 字符句一次拆成 8 句成功。

## 56. v8 实施修正（2026-08-18 实测）

**worker 被杀会留下僵尸 run。** 高危重转写被确认执行后 worker 重启，执行中的
run 永远挂在 `running`——活跃判定、串行重跑脚本全被堵死。修法是编排系统的标准
**启动对账**（reconcile-on-boot，Temporal/Prefect 同款语义）：worker 启动时把所有
`running` 的 run/step 判「执行被中断」，working 状态的修复会话回位 open，卡在处理中
的视频按体检结论落位。实测重启即回收 1 条僵尸。

**浏览器把页签判为 hidden 时 rAF 整体冻结。** 词级卡拉OK是纯 rAF 驱动，在自动化
面板里会"假死"——真实使用（页签可见）无此问题；用带时间戳的采样确认了可见状态下
词高亮与词级时间轴逐词吻合。

**中途换轨要硬失效。** 后台重跑把字幕轨整个换新（旧轨删除、新轨新 id），已打开的
学习页仍握着旧轨查询缓存。属已知可接受行为（刷新即好），列入后续优化（SSE 通知
track 失效）。

## 64. v9.2 字幕停留与音量控件（2026-08-18，scholar 两点反馈）

### 背景与调研结论（这条推翻了最初的做法）

scholar 的判断是"一句念完不该马上消失，下一句还没来就该留着"。方向对，但**实现口径不对**：

| 来源 | 原文口径 |
| --- | --- |
| BBC Subtitle Guidelines v1.2.5 §5.2 | 明确把"字幕留到下一条出现为止"列为**解码器的非合规行为**（non-compliant behaviour）；解码器应尽量贴合文档给定的出入点 |
| BBC §4.5 | 句间空隙"必须至少一秒，最好一秒半，更短会产生明显的跳动感（jerky effect）" |
| Netflix TTSG · Subtitle Timing | 24fps 下 3–11 帧的空隙**必须补掉**，做法是**延长上一句的出点**；空隙"要么 2 帧，要么半秒以上" |
| BBC §5.2 | lead-out（语音结束后挂留）**封顶 1.5 秒**；§5.1 补充理由：留太久观众会重读，是理解问题 |
| Karamitroglou 1998 | lagging-out 绝对上限 2 秒 |
| Netflix TTSG | 后面没有字幕时，出点"至少延到音频结束后半秒" |
| HTML "time marches on" / WebVTT / EBU-TT-D Annex E | 平台层没有"留到下一条"的语义，cue 只在 `[start, end)` 内渲染；EBU-TT-D 要求尽量贴出点移除 |

所以业内做法是**在成片阶段改出点**，而不是让播放器把过期字幕挂着。本项目的字幕来自 ASR + 强制对齐，没有人工出点，等于这道"补空隙"的工序从来没做过——于是在播放器里按同一口径**算出显示出点**，效果等价于成片补出点，且不违反"不得无限期挂留"。

排除项：EBU R 110 与 EBU Tech 3350 是格式/交付规范，不含计时数值，不可作为计时依据；网上流传的"BBC 规定 3 帧间隔"在 v1.2.5 全文中不存在，属讹传。

### 需求

- FR-121 **内嵌字幕显示出点**：显示出点 = `下一句开始 < 本句结束 + 1000ms ? 下一句开始 : 本句结束 + lead-out`。
  - **短空隙桥接**（< 1 秒，BBC §4.5 阈值）：无条件生效，与用户偏好无关——消抖动是规范要求不是口味。
  - **lead-out 档位**（播放器设置内）：不停留（严格按出点） / 标准 **1.5s**（BBC §5.2 封顶值，默认） / 长驻 3s（超出规范，为跟读抄写保留）。
  - **暂停时不倒计时**：停下来抄写正需要字幕在，恢复播放后按当前播放位置重算剩余停留。
  - **倍速折算**：停留是媒体时间口径，2× 播放时墙钟等待减半。
  - **跳转清理**：seek 到显示区间之外立即清掉，不留陈旧字幕。
  - **淡出后真正卸载**：仅靠 CSS `opacity` 过渡不够——`.vm-kw` 是 `pointer-events: auto`，透明但仍在 DOM 的字幕会吃掉"点画面暂停"的点击；淡出 280ms 后整块卸载。
- FR-122 **音量改竖向弹层**：悬停/聚焦从音量键向上弹出竖向滑杆 + 百分比读数，滚轮 ±5%。
  原横向滑杆是 hover 展开 0→72px，会把整条控制栏后面的按钮顶着走位；竖向弹层让控制栏宽度恒定。
  Netflix web / B 站 / Plex 用竖向，YouTube 用横向展开（它靠固定宽度容器吸收位移，本项目控制栏是流式布局吸收不了）。
  滚轮实现走原生非被动监听：React 的 `onWheel` 在 root 上是 passive 的，`preventDefault()` 无效会让页面跟着滚。

### 验收

## 66. v9.4 全屏浮层（2026-08-18，scholar 反馈）

### 根因

视频全屏时点字幕里的单词，词卡不出现。不是点击没生效，而是**卡片压根不在全屏子树里**：

Fullscreen API 规定只渲染全屏元素及其后代。本项目全屏的是 `.vm-screen`（视频画面 div），
而 `WordModal` 是渲染在页面根 `.main` 下的兄弟节点——全屏期间它仍在 DOM、仍有 `position: fixed`，
但浏览器不会把它画出来。同类问题还有 `?` 快捷键帮助浮层。

排除的两种改法：

- **把全屏目标换成整页容器**：能一次解决所有浮层，但控制条、右栏字幕列表都会被拉进全屏，
  得重写一套全屏布局，改动面远超收益。
- **改用 `<dialog>` / Popover API 走 top layer**：全屏元素本身也在 top layer，后进入的模态
  确实能盖在上面，但要把现有词卡整体换成 `<dialog>` 语义，且旧 Safari 支持不齐。

### 需求

- FR-127 **全屏浮层宿主**：新增 `components/FullscreenPortal.tsx`，全屏期间把浮层 portal 进
  `document.fullscreenElement`，退出全屏自动回到原位。挂载点：词卡 / 词组卡（`WordModal`，
  阅读器与视频页共用，阅读器不进全屏时为无操作）、快捷键帮助浮层（`ShortcutHelp`）。
  兼容旧 Safari 的 `webkitFullscreenElement` 与 `webkitfullscreenchange`。

### 验收

- AC-52 全屏时点字幕单词，词卡出现在画面中央，内容与非全屏一致。
- AC-53 退出全屏后词卡回到页面根下，行为不变。

## 68. v10.5 采纳闭环修复：三个问题叠成的死循环（FR-140）

scholar 问「每次采纳写回之后是需要重跑中文轨吗，而且每次跑完中文轨又会出现问题」。
是设计缺陷不是偶然，三个问题环环相扣：

```
采纳「疑似错词」→ 原文变了 → text_zh 置空 → 体检报「译文缺 4/109」
   → 用户重跑中文轨（downstream）→ 连带跑 verify
   → verify 把该视频问题清单 DELETE 全表重建 → 采纳/忽略记录全没了
   → LLM 无参考裁判重新judge 109 句 → 又冒一批新问题 → 回到第一步
```

数据坐实：视频 5 用户采纳 15 条后重跑中文轨，`accepted` 记录归零、新增 12 条 open；
而同期我测试过但没重跑 verify 的视频 7/9/15，59 条 accepted 全都还在。

### 三处修复

- **① 采纳原文修改即自动补译，不惊动整条管线**：`patch_issue` 置空 `text_zh` 后直接
  入队 `translate_track`（它自带「已有译文即跳过」，只补空缺那句），**不走 DAG**——
  走 DAG 会连带跑 enrich 与 verify，verify 又重刷问题清单，正是死循环的入口。
  响应新增 `queued_translate`，前端行内提示「后台正在只补这一句的译文」。
- **② verify 保留人工决定**：`_store_issues` 从 `DELETE 全表` 改为**只删 `open`**。
  问题是产物的函数，但**人的决定不是**。
- **③ 两条抑制规则**，避免把人处理过的又端上来：
  - 同一句同一类**已被忽略**过 → 不再冒（人说过"这不是问题"，就该记住）
  - 建议与句子现有文本**一致** → 不插（LLM 建议改成它已经是的样子，纯噪声）

### 实测（2026-08-18）

| 验收 | 实测 |
| --- | --- |
| 自动补译 | 视频 17 句 2612 采纳 `enoki→gnocchi`：原文写回、译文置空、`queued_translate: true`，worker 随即补出「自制意式团子其实非常简单…」（原译文是「制作金针菇…」），全程未碰整条中文轨 |
| 采纳留存 | 该视频 verify 重跑前后 `accepted` 均为 1 条（旧逻辑下会被删光） |
| 忽略抑制 | 忽略句 2548 的 `wrong_word` 后重跑 verify，该句该类问题**未复现**，只剩那条 dismissed |
| 噪声过滤 | 同一轮 verify 后 open 从 31 降到 24 |
| 质检 | ruff 全过、196 测试全绿、tsc 全绿 |

### 仍需知道的

LLM 无参考裁判本身是**非确定性**的：同一批句子重跑仍可能挑出不同的问题，这是
LLM-as-judge 的固有性质，不是 bug。上面三条规则把「人已处理过的」挡在外面，
但**新一轮仍会有新问题冒出来**——正确的用法是把它当作持续的质检建议，
而不是"处理完就归零"的待办清单。

## 69. v10.6 去重工具与补译时序（FR-141/142）

### FR-141 修复代理缺「去重」手段

scholar 遇到代理回复「当前工具箱不支持删除指定的非相邻重复句…只能保留该重复分句」。
代理的表现其实是对的——**它没有伪造修复**（明确报 `applied: 0`），缺的是工具。

新增 `mark_noise(sentence_id, noise=True)`：**软删除而非真删**。

`is_noise` 是既有语义，字幕列表、播放序列、AI 校验、陪读上下文、体检的 speech 统计
**全都已经按它过滤**，标了就等于从学习链路消失。比硬删好在三点：

- 时间轴与 cue 归属不用重排（避开「负数占位两段式」那套序号坑）
- 误判可一键撤销（`noise=False`）
- 原始转写留档可追溯

实现细节：**不调 `_mark_dirty`**——文本没变，译文与词组区间依然有效，
清掉反而会让体检报「译文缺」并触发无谓重译。

系统提示同步更新，明确「重复句、纯口水句用 mark_noise，不要试图靠合并/改写去消除，
也不要因为『没有删除工具』就说修不了」。

### FR-142 「译文缺」偶发误报

scholar 反馈上一版的译文缺问题「偶尔还出现，多刷新几次就没了」——是时序问题：
**置空译文是同步的，补译是异步的**，中间几秒任何体检都会看到缺口并报 `error`，
把视频判成 degraded。

- 采纳原文修改入队补译时，在轨 `meta.zh_refill_at` 打时间戳
- 体检读它：3 分钟宽限期内把 `translation_gap` 从 **error 降为 info**，
  文案改成「N/M 句译文正在补齐（采纳原文修改后自动触发）」，gate 不再误判
- **补译完成后清掉时间戳**——留着的话宽限期内的真实缺失会被当成"正在补"而漏报

### 实测（2026-08-18）

| 验收 | 实测 |
| --- | --- |
| 去重工具 | 标记后 `is_noise=True`、**译文保留**（未被误清）、`noise=False` 可撤销 |

## 70. v10.7 修复流程重构：从「一条一对话」到「一键全修」（FR-143~145）

scholar 的判断：「AI 只能一个个修复，不能一次性把所有问题都发给 AI 吗？AI 应该赋予
一定的功能能力才对，感觉多轮对话修复也没有必要」。**成立，而且根因比"不能批量"更深。**

### 根因：校验的输出 schema 只有一种表达力

查库：81 条可一键采纳、33 条不能。这 33 条**全都有句号、全都没建议**：

| kind | detail 说的 | 但 suggestion 为空 |
| --- | --- | --- |
| `noise` | 「无内容的停顿标记，**应当清理**」 | 清理不是"改成某段文本" |
| `bad_split` | 「"Hello." 疑似断句过细」 | 正确动作是**合并** |
| `wrong_word` | 听错了但拿不准正确词 | 需要查证 |

裁判只会说「把文本改成 X」，凡是修法不是文本替换的（去噪、合并、拆分、重跑节点），
它只能留个空建议——于是这些问题一键采纳处理不了，用户只能一条条进对话。
**对话不是设计出来的形态，是 schema 表达力不足挤出来的。**

### FR-143 给校验一套动作词汇表

裁判输出新增 `action` + `anchor`：`replace_text` / `replace_translation` /
`mark_noise` / `merge_prev` / `merge_next` / `split_at` / `manual`。
配套 `sentence_ops.apply_issue_action()` 按动作分派到对应领域操作，
「采纳」不再只会替换文本。

自洽性校验：动作与内容对不上（如 `replace_text` 却没给 suggestion、`split_at` 没给
anchor）**自动降级为 manual**，免得端上一个点了必失败的按钮。旧数据无 action 字段，
按 kind + 有无建议兜底，行为与 v10.6 完全一致。

### FR-144 一键全部修复

`POST /pipeline/videos/{id}/autofix`：
1. **先用确定性分派批量落地**能自动执行的（不烧 token、不等模型）
2. 剩下 `action=manual` 的**打包成一份任务清单交给代理**——一个会话处理全部，
   不是一条一个对话
3. 原文改动触发的补译一并入队

### FR-145 修复后的验证不再重跑 LLM 裁判

实测视频 10 暴露：代理收尾调 `run_verify` 跑的是完整 verify（含 AI 裁判），
于是刚清完的 40 条转眼又冒出 37 条新的。裁判是非确定性的，
**每修完一轮就重判一次，必然永远处理不完**。改为只做确定性体检
（`config_override={"verify": {"ai_review": False}}`）；要重新过 AI 校验，
由用户显式点「重新体检」——那是他的决定，不该是修复流程的副作用。

### 对话保留，但降为逃生通道

不同意完全删掉，理由三条：① 你自己发现而裁判没查出的问题需要入口；
② 「换更强模型重试」需要会话；③ 高危动作确认需要交互。
但它从主路径降为「自动修完还不满意 / 另有发现」时才用。

## 71. v10.10 节点实时进度与耗时预估（FR-148）

执行中的节点此前只有「进行中」三个字，耗时显示「—」，等多久全靠猜。

### 进度从哪来：两个来源，优先真实的

- **真实百分比**：download 按字节、transcribe 按音频段实时回写 `video.progress`。
  给 `StepSpec` 加 `progress_span`（该节点在整体 0-100 里占的区间），
  前端换算 `(整体进度 - span[0]) / (span[1] - span[0])` 得到"这一步跑到哪了"。
  区间定义原先散在 worker 的 `_STEP_PROGRESS` 里、与节点定义分离，
  已搬到 `domain/pipeline.py` 与 `StepSpec` 同源，worker 改为查表视图，消除漂移。
- **历史推算**：没有细粒度上报的节点（标点/对齐/翻译等），用
  `已用时 ÷ 历史耗时中位数` 估算。载荷新增 `eta` 字段：按节点给出历史成功执行的
  **中位数**（均值会被一次异常慢跑拖偏）、样本量、最快/最慢。

### 三条「不撒谎」的规则

1. **样本 < 2 次不给 ETA**，只显示秒表，并说明「首次执行，无历史可参考」——
   拿一次样本外推是编数字。
2. **超出预估不继续爬也不倒数成负数**，切成不确定态并明说「已超出预估，仍在执行」。
3. **推算的进度条画成条纹**，与真实上报的实心条视觉可区分——不能让人误以为是实测值。

### 展示

- 抽屉顶部：秒表（每秒走）+ 进度条 + 「约剩 X」/「已超出预估」+ 依据说明
  （「实时进度 72%」或「按历史中位数推算（N 次样本：最快–最慢）」）
- 节点本身底部一条 2px 细进度条，不点开也知道跑到哪了

### 顺带修掉的深链 bug

实测发现 `?node=` 深链进来后选中被立刻清掉。根因是「切运行记录时收起详情」那个

### 72.5 朗读收口与图标可辨识（scholar 三点反馈）

- FR-348 跟读工作台点原句走**片段播放**，读到句尾即停。原实现是裸 `el.play()`，原句读完视频一路往下跑，跟读节奏全乱——播放器早有 `segRef` 片段机制，直接用它。
- FR-349 图标操作条改用**即时提示**（radix Tooltip，`delayDuration: 0`）。原生 `title` 要悬停一两秒才浮出来，八个图标挤在一行时等于没有提示；同时补 `aria-label`，读屏可用。
- FR-350 **浮层关闭即停朗读**，全产品一致：词卡、语法分析、跟读工作台、音色选择、短文全文。抽成 `useStopTtsOnClose(open?)` 一个钩子，不逐个弹窗手写清理。

> [!warning] 常驻组件的"关闭"不是卸载
>
> `WordModal` 是常驻的——栈空时只 `return null`，组件从不卸载，
> 所以只挂 `useEffect(() => () => stopTts(), [])` 的清理**永远不会触发**，关掉词卡声音照响。
> 这类组件必须把打开态作为依赖，由 true→false 的切换触发收尾。
>
> 这个 bug 差点漏掉：`document.querySelectorAll('audio')` 查不到 `new Audio()` 创建的元素（它不在 DOM 里），
> 头一次验证读到"关前关后都是 0 个在播"，看着像通过。改成给 `HTMLMediaElement.prototype.play/pause` 插桩记事件才暴露出来。

### 72.7 提示全局化与弹窗内朗读一致（scholar 三点反馈）

- FR-357 **全产品的 title 提示统一即时浮出**。产品里有 255 处 `title`、散在 70 个文件，逐个换成组件不现实、新代码也会忘——改成在 App 层做一次**事件委托**接管：悬停时把 title 摘到 `data-tip`（原生提示就不再弹），离开时原样放回。现存的全部自动升级，以后照常写 `title` 即可。

- FR-359 弹窗内的**词级卡拉OK高亮**与外面一致。原句一律走**视频片段播放**而不是 TTS——词级时间戳是视频的，另合成一段 TTS 时间轴对不上，高亮必漂。为此把语法弹窗提到页面层，与跟读弹窗共用同一份播放控制与高亮驱动。

> [!warning] 只挂 rAF 的高亮在页签不可见时会整个停住

> 卡拉OK首版只用 `requestAnimationFrame` 驱动，页签 hidden 时 rAF 被浏览器整体冻结，高亮直接不动。
> 改成 **rAF + `timeupdate` 双通道**：可见时逐帧顺滑，不可见时由 `timeupdate`（约 4Hz，hidden 下照常触发）兜底。
>

> 一度以为是接线没通。CLAUDE.md 里早记过"rAF 在 hidden 时冻结"，但当时只当成验证障碍，
> 没意识到它同时是产品缺陷——**验证环境暴露的异常，先当真实缺陷查，再当环境问题绕**。

### 72.8 弹窗原句的重读与译文（scholar 反馈）

- FR-360 跟读与语法弹窗的原句加**从头读**按钮。播放按钮是「续播/暂停」语义（BR-G-015），回不到句首；想重听一遍原本没有入口。两个动作语义不同，做成两个按钮而不是挤在一起。
- FR-361 原句下方显示**译文**，取字幕句自带的 `text_zh`——与视频里看到的完全一致，不用 AI 再翻一遍。语法分析结果里的 `translation` 降级为兜底：只在调用方没有译文时才用（阅读器等场景仍需要它）。

> [!note] 为什么不直接从 grammar prompt 里删掉 translation
>
> 语法分析按内容指纹缓存（ADR-006），缓存键只认句子内容、不含 prompt。
> 若按"调用方有没有译文"分别产出，同一句会出现两种结果争抢同一个缓存键。
> 而 `translation` 只是整个分析里的一个字段，省下的调用成本远不如缓存一致性重要——
> 所以后端照旧产出，由前端决定优先显示哪一份。

## 73. 重跑句层进高危确认门（2026-08-24 审视发现）

`RISKY_STEPS` 原先只有 `("download", "transcribe")`，判据是「开销高」。但
`build_sentence_layer` 的第一句是 `delete(SubtitleSentence)`，而
`study_unit_state`（已学✓/收藏/旗标/听写成绩）与 `shadow_recording`
（录音 + 逐词比对 + AI 点评）都是 `ondelete=CASCADE`——**重建一次句层，
用户攒下的学习痕迹全没，不可撤销，磁盘上的录音变孤儿**。

而修复代理的系统提示词第 50 行恰好写着「大面积断句碎/黏 → rerun_pipeline(sentences)」，
所以跟 AI 说一句「句子切得太碎」就会自动触发，无任何提示。BR-25 的原话是
「高开销/**破坏性**修复操作需一次人工确认」，破坏性那一半此前没有落地。

改动：拆成 `COSTLY_STEPS` 与 `DESTRUCTIVE_STEPS` 两类，`RISKY_STEPS` 是二者之和。
重跑 scope 是 downstream，所以句层**上游**的 `punctuate`/`align` 同样连带重建，
一并入门。

> [!danger] 两类原因的确认文案必须分开写
>
> 拿「整片重新处理，以分钟计」去描述一个会删学习记录的操作，等于给了错的说明——
> 用户看到「开销大」只会想「那我等等」，不会想到「我的跟读录音要没了」。
> `confirm_reason()` 按类型出文案，守卫在 `tests/test_repair_risky_steps.py`。

**仍未做（等 scholar 定）**：重建时把学习状态与录音按归一化词序列迁移回新句，
而不是删掉。当前只是拦住了自动触发，用户点确认后照样会丢。

### 三条判据值得单独记

> [!danger] 用白名单列「进行中」，不要用排除法列终态
>
> `busy = status !== 'ready' && status !== 'failed'` 这种写法，**每加一个终态都会被
> 当成进行中**。degraded 就是这么变成永久转圈的：页面等一个永远不会来的完成信号，
> 还每 3 秒轮询一次。改成 `isBusyStatus()` 与 `BUSY_LABELS` 同源，加终态不会再重演。

> [!danger] 同一份数据有两套编号时，跨体系取号不会报错
>
> 后端按 `SubtitleCue.ordinal` 记词卡出处，前端拿它去 `StudyUnit` 数组里查
> （424 条 vs 685 条）。类型都是 number，编译器无从发现，界面上只是「显示了另一句话」。
> 同族的还有 `syncLibEntry` 四个 number 形参——漏改一处会把秒数灌进「已学」位，
> 短视频当场显示「已学完」，**tsc 一声不响**。这类只能靠 grep 全仓逐个核对。

> [!warning] memo 与虚拟化要一起做，缺一个等于没做
>
> `SentenceCard` 早就 memo 了，但 9 个内联回调让浅比较必然失败；而播放中
> `onTimeUpdate` 每秒 setTime 约 4 次。只虚拟化不稳定回调，窗口内那十几张照样每秒重渲 4 遍。

### 句层重建的学习记录迁移

不再「先删后建」——**新句先占负序号与旧句共存 → 迁移 → 显式删旧行 → 落回正序号**。
两个理由：删了旧句就没有旧文本可比对；`shadow_recording.sentence_id` 是 NOT NULL，
先删就必须先扔掉录音。旧行清理全部走显式 DELETE/UPDATE 不靠 CASCADE
（内存 SQLite 不开外键，靠 FK 会让 SQLite 与 PG 行为不一致而测试全绿）。

匹配复用 `sentence_ops._locate`（归一化词序列），双向命中分别覆盖并句与拆句；
时间重叠只在同分时裁决。存量 3024 条学习句实测：同阈值重切 **99.83%**、
收紧 99.80%、放宽 99.74% 能落点；落不了的计入 `SubtitleIssue`（kind=`records_lost`）
而不是静默消失。

确认门文案随之改口径：迁移上线后再说「无法恢复」同样是**错的说明**，
用户会从此不敢调断句。现在说的是「译文与词组会清空；学习记录尽量迁移，
迁不过去的列进问题清单」。门保留——迁移是尽力而为。

## 75. 视频库栅格与筛选完善（2026-08-24）

- **一行 6 张**（4 → 5 → 6，2026-08-25 再加一档）。1800 视口卡宽 261px、缩略图 261×147，
  认得出是哪个视频。密度上限实测在 6：24 张卡里 7 列有 6 条标题被截，6 列只有 2 条。
  阶梯 `6 / 5 / 4 / 3 / 2`，断点 1700 / 1400 / 1120 / 860，每档卡宽都落在 230~310——
  若只把顶档从 5 改 6、不补 5 那一档，1700 处会从 6 列（244）直接掉到 4 列（375），跳 54%。
  顺带删掉一条重复规则：文件末尾的 `@media (max-width:1000px)` 在后面，把前面 900 那档整个盖死了。
- **筛选条件进 URL**：搜索词 / 难度 / 口音 / 主题 / 时长 / 状态 / 排序全部落 query。
  以前只有 `tab` 进 URL，筛半天一刷新全没了，也没法把某个筛选视图存成书签。
  多选集合走新加的 `useUrlSet`（逗号分隔，空集合不留参数），与既有 `useUrlValue` 同一模块。
- **「最近学过」排序**：顶部「继续学习」只显示最近一条，同时开着三四个时，
  其余在「最新导入」里早被冲到后面。数据本来就有（`LibEntry.lastAt`），只是没接。
- **筛选计数带分母**（`筛选结果 · 3 / 24`）：只报「3 个视频」时，用户分不清是自己筛太狠
  还是库里真就这么点。

> [!danger] 卡片密度是被 chip 卡住的，不是被缩略图卡住的
>
> 加密到 6 列时，带 3 个标签的卡上 chip 全花了：`.chip` 是 `height: 20px` 固定高
> （tokens.css），被压窄后文字在里面折成两行、再被固定高截掉半行。
> `.vm-vmeta` 上已有的 `overflow: hidden` 挡不住——它挡的是行，不是 chip 内部。
> 修法是 `.vm-vmeta .chip { flex-shrink: 0 }`：chip 保持自然宽，装不下的由行边缘整齐切掉，
> 读作「还有更多标签」。
>
> **查这个坑不能用 `scrollWidth > clientWidth`**：文字换行不产生横向溢出，那道检查恒为 0，
> 我第一遍就是这么漏掉的，靠 device 分辨率的单卡截图才看出来。要测 `scrollHeight > clientHeight`。

> [!danger] `setSearchParams` 不是 `useState`：同一事件里连调只有最后一次生效
>
> 「清除筛选」原先连调六个 setter。筛选还是组件 state 时没问题，一改成 URL 支撑就露馅：
> `setSearchParams` 触发的是**导航**，同一事件里每次都读到导航前那份 location，
> 后一次覆盖前一次。实测点「清除筛选」只清掉了 `state`，`accent` 与 `diff` 原样留在 URL 上。
> 清空这类要**一次 `patch({a: null, b: null, …})` 写完**。约束已写进 `lib/urlState.ts`。
