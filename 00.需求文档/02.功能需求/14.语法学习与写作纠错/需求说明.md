# 语法学习与写作纠错

## 1. 模块目标

语法不是背规则，是**在自己读过的东西里认出结构、在自己写的句子里发现偏差**。

本模块的差异化不在讲解质量（那是 LLM 的活），而在**能把语法点绑到用户自己的语料上**——
书库、字幕、场景短文都在库里，带 TTS、带词级时间戳、带现成的语法弹窗。任何通用语法 App 都做不到这件事。

## 2. 现状盘点（2026-08-19 核实）

| 已有 | 状态 |
| --- | --- |
| LLM 语法分析 | `grammar-deep` 别名 + `grammar_prompt()` + 176 行句子级弹窗（模块 05） |
| 分句与词元 | pysbd 分句 + 正则切词，记 UTF-16 偏移 |
| FSRS 调度器 | `domain/srs.py` 已用于单词 |
| 前端图渲染 | **`@xyflow/react` 12.11 + `dagre` 已装**（管线 DAG 图在用） |
| 语料 | 41 本书 1716 章 64188 段落、68 个视频带词级对齐字幕、场景短文 |

**缺口**：无语境词性标注、无依存句法、无语法点目录、无写作纠错。

> [!warning] 一处文档与实现不符
>
> 需求文档模块 02 的实现方案表写着「分句/词元用 spaCy en_core_web_sm」，
> 但代码里 grep 不到任何 `spacy` import，实际是 pysbd + 正则。
> 模块 01 的 v2 文档还明确写过「不引入 spaCy 运行时」。
>
> **所以本模块引入 spaCy 是新增依赖，不是「已有但没用起来」。**

## 3. 内容组织：三层索引，不是三选一

「按语法点 / 按句型 / 按错误类型」单选都会漏。三者是同一批数据的三个索引面。

### 3.1 L1 语法点目录（骨架，FR-400）

- FR-400a 以 **CEFR-J Grammar Profile** 的 **499 条**建 `grammar_point` 主表。
  这是唯一许可写明「研究与商业均免费、需正确引用」的机器可读清单，且已交叉映射到
  EGP / Core Inventory / GSELO 三套体系，省掉自己做对齐。
- FR-400b 字段直接落库：`shorthand_code / item / sentence_type / cefr_level / egp_level / core_inventory`。
  `Notes` 列是日文，用 LLM 批量翻译一次落库。
- FR-400c **English Grammar Profile**（1240 条）只作为挂在语法点下的**补充素材**——
  它的 Can-do 陈述与带母语标注的真实学习者例句是好讲解料，但无许可证，个人自用不再分发。
- FR-400d 编排抄 *English Grammar in Use*：**一个语法点 = 一屏，上讲解下练习，
  按语法范畴分组而非难度排序，允许乱序进入**。

> [!note] 粒度已经够细，不用再切
>
> CEFR-J 的 `Sentence Type`（AFF./NEG. × DEC./INT.）本身就把「be 动词」拆成了
> `I am / I am not / Am I / Am I not` 四条，已经是可判定的题目粒度。

### 3.2 L2 构式识别（本模块的核心价值，FR-401）

- FR-401a 用 spaCy `DependencyMatcher` 写 **30-50 条**高频构式规则（不是 1240 条），
  在已有的书库/字幕/场景短文里标出该语法点的真实出现。
- FR-401b 用户点一个语法点 → 「你上周读的那本书第 3 章有 7 句用了这个结构」→
  点进去跳原文，带 TTS、带词级对齐、带现成的 `grammar-deep` 弹窗。
- FR-401c 语义细腻的长尾交给 LLM 兜底，不追求规则全覆盖。

### 3.3 L3 误区与错题本（FR-402）

「答错」不建模成「不等于正确答案」，而建模成**可命名的具体误区**（misconception）。
这条抄 [oppia/oppia](https://github.com/oppia/oppia)（Apache-2.0，★6771，2026-08-19 仍在推）
的教育领域模型：

```
答案规则  →  命中某个误区  →  定向反馈  →  跳转补救内容  →  再练对应题
```

一个真实例子：

| 环节 | 内容 |
| --- | --- |
| 技能 | 一般过去时否定句 |
| 学习者答案 | `He didn't went there.` |
| **误区** | `didn't` 之后仍用过去式 |
| 定向反馈 | 时态已经由 did 承担，后面的动词恢复原形 go |
| 补救 | 助动词与实义动词的时态分工 |

- FR-402a 用 **ERRANT** 的 `M/R/U × 25 类` 做归档维度，**不自己发明错误分类体系**。
- FR-402b 常见误区在出题时**预先绑定**在题目上（`misconceptions: [{pattern, id, feedback, remedial_point_id}]`），
  没命中任何预设误区时才降级到 LLM 自由讲解。
- FR-402c 误区 id 与 ERRANT 的 55 类标签双向映射：写作纠错命中的 ERRANT 类型能定位到误区，
  误区能反查该补哪个语法点。
- FR-402d 用户写错一次 `R:VERB:SVA`，系统把主谓一致相关的语法点提前。

> [!note] 为什么值得比「LLM 写段评语」多做这一层
>
> **误区是有限的、可枚举的、可统计的**。它能回答「你这个错误犯过 5 次」和
> 「这类错误该补哪一课」，LLM 的自由文本回答不了这两个问题。
> LLM 退到兜底位置——只处理没预设过的长尾。

## 4. 写作纠错：必须两段式（FR-403）

> [!danger] 一步式的实测覆盖率只有 40.6%
>
> NAACL 2024 Findings 的数据：把整句丢给 GPT-4 让它「找错并解释」，
> **只覆盖 40.6% 的错误**。整句一次过是错的架构。

正确流水线：

```
学习者原句
   ↓
LLM 产出修正句
   ↓
ERRANT 对齐成原子编辑（M/R/U × 25 类）
   ↓
每条编辑单独喂 LLM 生成中文讲解
   ↓
按 ERRANT 类型归档进错题本 → 关联语法点 → 进 FSRS
```

- FR-403a ERRANT 需要「修正句」作为输入，修正句先由 LLM 产出。
- FR-403b 打字时的即时红线用 **Harper**（Apache-2.0，WASM，浏览器端跑，服务器零成本）。
- FR-403c Harper 必须 `import()` 懒加载——实测 wasm **16MB 原始 / brotli 后 6.7MB**，绝不能进主 bundle。
- FR-403d Harper 是规则型，抓表层错误，**不能替代** LLM 讲解深层结构问题。

### 4.1 规则检查分两级，LanguageTool 是有条件的第二级

- FR-403e **一级（默认）**：Harper 在浏览器里跑，输入过程即时标线。服务器零成本。
- FR-403f **二级（可选）**：提交后由服务端做深度复核。

二级默认不开。**开启的触发条件**是以下任一成立：

1. Harper 的规则覆盖被实测证明不够——用自己的错句样本跑一遍，漏检率高到影响使用；
2. 需要英美变体区分（写作时要求统一 en-US 或 en-GB）；
3. 需要稳定的规则 ID 做长期统计（Harper 的规则标识不保证跨版本稳定）。

满足时才引入 [LanguageTool](https://github.com/languagetool-org/languagetool) 作为
**Java sidecar**（LGPL-2.1，★14.8k，2026-08-19 仍活跃），调用形状：

```
FastAPI
  → LanguageTool /v2/check
  → ruleId / category / offset / replacements
  → 映射到内部 misconception_id 与 grammar_point
  → LLM 只负责把规则命中翻译成中文讲解
```

它的价值在**规则 ID 稳定且自带正反例测试**，适合做「错误类型 → 语法点」的确定性映射；
代价是常驻 JVM。在这两者之间，**先用 Harper 跑一段时间再决定**，不要预先上。

> [!info] 分工原则
>
> 规则判定（Harper / LanguageTool）给**确定性结果**，LLM 只负责**解释**，
> 不单独决定对错。这与 §4 两段式纠错、与音标模块 BR-90「不让 LLM 打分」是同一条原则。

## 5. 练习形式（FR-404）

题型的渲染与判分走
[组件：练习引擎](../../../01.项目文档/02.架构/C4模型/组件-练习引擎.md)，
本模块只出内容与判分规则。按 structured input 的顺序排：

| 序 | 题型 | 说明 |
| --- | --- | --- |
| 1 | **指称型结构化输入** | 有唯一正确答案，且必须靠目标形式才能取义。例：播一句 TTS "He worked at the bank"，问「说的是现在还是过去」——语义线索被剥掉，只能靠 `-ed` |
| 2 | 情感型结构化输入 | 无对错。给 5 句含目标结构的句子，勾「符合我的情况」。巩固用，不计分不进 SRS |
| 3 | 语料定位题 | 在自己读过的书/看过的视频里找出该结构。复用 L2 的匹配结果，零 LLM 成本 |
| 4 | 产出型 | 中译英 / 句子改写 / 词块排序。提交后走 §4 的两段式纠错 |
| 5 | 错题回炉 | ERRANT 类型 → 对应语法点 → 进 FSRS |

> [!info] 第 1 类是本项目的独家优势
>
> Lee & VanPatten 要求结构化输入「口书两种输入并用」。本项目有豆包 TTS（可指定音色）
> 与真实字幕音频，能真的做出**听力版**语法题；其它 App 只有文字选择题。
> 每个语法点先出 2-3 道。

## 6. 可视化（FR-405）

### 6.1 默认视图是句内成分着色，不是树图

- FR-405a **默认**：主/谓/宾/状用底色标出、从句可折叠成一个色块。纯 CSS + span，零渲染成本，
  直接服务「看懂长句」这个真实需求。
- FR-405b **二级入口**：依存关系图，用**已装的 `@xyflow/react` + `dagre`** 渲染，零新增前端依赖。
- FR-405c 节点是 React 组件——点节点能查词、播 TTS、跳回原句。这是把树图从「装饰」变成「入口」的关键。
- FR-405d 服务端**只返回 JSON**（`{words:[{text,tag,lemma}], arcs:[{start,end,label,dir}]}`），
  不用 `displacy.render` 直出 SVG：那是给语言学家看的静态弧线图，前端没有交互余地，且直出 HTML 有 XSS 风险。
- FR-405e spaCy 的依存标签是 ClearNLP/OntoNotes 风格（`dobj/pobj/prep/attr`）**不是 UD**
  （`obj/obl/case`），网上找的 UD 中文对照表不能直接用；45 条中文标签映射表要自己写。

### 6.2 与现有 LLM 弹窗的分工

- FR-405f 现有 176 行语法弹窗**保持不动**：spaCy 讲「是什么结构」，LLM 讲「为什么」。
- FR-405g 两者结论不一致时**以 LLM 为准并静默记日志**——`en_core_web_sm` 的 DEP_LAS 是 89.87，
  长难句会分析错。

## 7. SRS 接法（FR-406）

- FR-406a **一题一卡，不是一语法点一卡**。一个语法点挂 N 张卡。
- FR-406b 只调度第 1 类与第 4 类里**可自动判定**的题。口头产出继续走模块 09 的跟读比对，不塞进 SRS。
- FR-406c 评分 1-4 直接喂现有 `domain/srs.py` 的 `review()` / `preview_intervals()`，**调度逻辑一行不改**。
- FR-406d `StudyUnit` / `StudyUnitState` 是字幕专用表（外键绑 `subtitle_sentence` 与 `track_id`），
  **不能复用**，新建 `grammar_card` / `grammar_card_state`。

> [!note] 间隔重复对语法有效，但有边界
>
> Bird (2010) 支持间隔对 L2 句法有效（60 天延迟后测差异更明显），
> 但 Suzuki & DeKeyser (2017) 提示流利产出阶段别指望间隔。所以只调度可判定题。

## 8. 业务规则

- BR-95 语法点目录以 CEFR-J 为唯一权威索引；EGP 只作补充素材，不做主索引、不再分发。
- BR-96 结构分析（spaCy）与讲解（LLM）职责分离；冲突以 LLM 为准并记日志（FR-405g）。
- BR-97 写作纠错必须先原子化再逐条讲解，禁止整句一次过（FR-403）。
- BR-98 错误分类沿用 ERRANT 的 55 类，不自建体系。
- BR-99 树图不做默认视图；任何结构可视化都要可点、可跳回原文，不做只读装饰图。

## 10. 明确不做

| 不做 | 理由 |
| --- | --- |
| **LanguageTool 默认不部署** | Java 常驻进程基线 ≈1GB RAM，加 n-gram 还要 8.34GB 磁盘。单人项目为它常驻一个 JVM 不划算，规则兜底先用 Harper。**但它不是永久排除**，触发条件见 §4.1 |
| **GECToR** | 需要 torch + AllenNLP，而本项目连 torch 都没装；BEA-test F0.5 仅 73.21，已低于可直接调用的 LLM（77.41）。为更差的结果新增 2GB 依赖，纯亏 |
| **成分句法树**（NP/VP/PP 嵌套） | 工具链本身断了：benepar PyPI 停在 0.2.0 / 2021-02 且要 torch |
| **全量 EGP 1240 条规则化检测** | 30-50 条高频构式已覆盖日常阅读绝大部分，长尾投入产出比断崖式下降 |
| 自训练/微调 GEC 模型 | 无 GPU |
| `explosion/displacy.js` | 2018-04 已归档，npm 包停在 1.1.0 |
| jssyntaxtree | GPL-2.0，前端引入有传染性 |

## 14. 实施记录（2026-08-19 全量落地）

### 14.2 一处需求与现实不符：501 不是 499

### 14.3 构式规则的实测形态

需求写 30-50 条，实际写了 **55 条**，每条都带一句自检例句、进单测逐条验证
（`test_every_rule_matches_its_own_example`）——规则写错要在单测里炸，

### 14.4 一处实现事故与修法

**误区目录的 seed 脚本第一版用 `TRUNCATE ... CASCADE`，把用户的错题本一起清空了。**
`writing_edit.misconception_id` 有指向 `misconception` 的外键，CASCADE 会连级联表一起截断。
现改为按 `code` 更新已有行、只插新增的，目录里删掉的误区**保留历史引用**只是不再新命中。
重跑 seed 不再伤数据。

### 14.5 出题时踩到的一个上游行为

批量出题走 LLM，上游偶尔会把某一批的 payload 判成内容策略违规（502）。首版遇到就整轮中止，
一批失败丢掉后面几百个语法点——**把偶发变成了阻断**。

改成单批失败不中止之后又发现第二层问题：整批丢掉会连累同批里没问题的点。
情态动词的 `may / must NEG / need NEG / need INT` 四个点每次都被拒，重跑多少次都一样。

最终做法是**整批被拒时逐条重试**：四个点单独发全部通过——被拒的是**合并后的 payload**，
不是其中任何一条。多花几次调用，换来把问题隔离到具体某一条而不是笼统地丢一批。
逐条也过不去的点会显式报出来（当前为 0 个），不静默截断。

## AI 语法分析的 components 是一棵树，不是列表（2026-08-25）

模型返回的 `components` 是**先序拍平的树**：一个成分，紧跟它内部的下级，再下一个平级。
线上缓存 17 条里 **11 条（64.7%）** 带两层甚至三层嵌套。

渲染器原先直接 `components.map(...)` 串成一行，于是整句出现两遍：

```
并列分句1  I'm from Hangzhou       ← 第 1 层
主语+系动词 I'm                     ← 第 2 层，上一条内部
表语       from Hangzhou           ← 第 2 层，上一条内部
并列连词   and
并列分句2  I live in Shanghai now  ← 第 1 层
主语/谓语/地点状语/时间状语              ← 第 2 层
```

两个渲染点都中招：`reader/SentencePanel.tsx`（阅读器 / 讲义库 / 场景短文共用）与
`video/GrammarDialog.tsx`。修复抽在 `reader/grammarTree.ts`，两处共用。

**不变量**：渲染出来的就是原句本身，逐字符相等。做法是渲染原句、给区间上色，
所以重复和丢字在构造上不可能发生。

> [!danger] 不能靠字符串包含关系猜父子
>
> 第一版用「a 的文字是不是 b 的文字的子串」判嵌套，被真实缓存打穿两处：
> ① `in possession of a good fortune` 在父串里紧跟逗号（`fortune, must be`），
>    按词边界比对两侧要空格，判不出来 → 掉回根层 → 重复；
> ② `at last`、`Lady Lucas` 是模型**乱序追加**的回指片段（下标 14/15，父在 11/13），
>    单调栈那时已把父弹掉。
> 还有第三类：`and` 这种短词句中出现多次，纯文本包含分不清是哪一个。
>
> 改成**按位置**：先定位到原句的字符区间，再纯按区间包含建树。且定位与建树**必须分两趟**——
> 混在一趟里，乱序来的成分会以正确位置挂在错误层级。
> 定位用三级回退：上一个成分的终点 → 上一个成分的起点 → 全句。次序不能反，
> 先起点会让分句层的 `and` 命中前一个列表里那个。

回归用真实数据守：`grammarTree.real.test.ts` 从 `analysis_result`（kind='grammar'）
导出 fixture，原句按 content_hash 关联 sentence + paragraph 还原，逐条断言渲染 == 原句。
构造用例覆盖不到紧贴标点、乱序回指、重复短词这三类形态。

## 成分角色收敛成固定枚举 + 阅读器面板只留依存图（2026-08-25）

### 为什么不是砍掉 spaCy

起因是「已经有 AI 做语法分析了，spaCy 是不是重复了」。查完的结论是**只重复了一块**：

| | 重复？ | 说明 |
| --- | --- | --- |
| 阅读器/视频面板的「成分着色」 | **是** | 正下方就是 AI 的 components 彩色块，同一个面板上下两块给同一句上同一套主谓宾状 |
| 依存关系图 | 否 | AI 的 prompt 压根不产依存树 |
| 语法页「句子实验室」 | 否 | 走 `/grammar/concepts/deconstruct`，带命中构式 + 指回讲义概念，且那页没有 AI 并排 |
| `scan_grammar.py` 全语料扫描 | 否 | 387,490 处 `grammar_occurrence`，撑着 FR-401b 与零 LLM 成本的语料定位题 |

而且**砍掉整条链路一分钱不省**：写作纠错用的 `errant` 自身依赖 spacy（`uv.lock`），
`writing.py:46` 注释也写明它内部另加载一份。磁盘 56MB / 常驻 ~130MB / 冷启动 ~1s 照旧。

所以只砍重复的那一块：`StructureBlock` 传 `only="tree"`，阅读器与视频面板的「句子结构」
只开依存关系图；语法页两个视图原样保留。

### role 必须是封闭枚举

> [!danger] role 自由，颜色就没有意义
>
> prompt 早先只写「中文成分名，如 定语从句/状语」，模型就放飞了：
> 实测 **108 个成分吐出 70 种 role 串**（`后置定语（过去分词短语，修饰 a truth）`、
> `help 的宾语`、`系表结构/被动表达`）。前端只硬映射 18 个词，其余按 `下标 % 4` 轮换颜色——
> 同一句重新分析一次颜色就变，「时间状语」和「地点状语」可能同色。
> **靠颜色记结构这个学习方式，在 role 自由的前提下根本不成立。**

枚举八类：`主语 / 谓语 / 宾语 / 表语 / 定语 / 状语 / 连接词 / 分句`（前端多一个兜底的「其他」）。
从句按它充当的成分归类：定语从句→定语、宾语从句→宾语、状语从句→状语。

**解释不是丢掉，是挪进 `note` 字段**。长尾里 `后置定语，修饰 ladies` 的后半是有价值的，
硬砍成枚举等于把它扔了。新 prompt 实测：7 个成分全部落在枚举内，解释整体迁进 note。

两头都收：
- prompt 端限定枚举（`domain/llm.py` 的 `GRAMMAR_ROLES`）
- 前端再兜一道（`features/reader/grammarRole.ts` 的 `normalizeRole`），
  把历史缓存的 70 种自由文本归一化过来——实测 70 种归到 8 类，只有 `插入强调成分` 一条落「其他」

两处枚举必须一致，由 `tests/test_grammar_roles.py` 读 TS 文件比对守住：
改一处漏一处不会报错，只会让新角色在前端静默变灰。

配套：高亮色从 4 个补到 9 个（原先表语和宾语共色、定语和状语共色），
每个角色一个色，`--gr-hue` 在 CSS 里只定义一次，填充与底线都从它取。

### 顺手修的两条

- **一次请求跑三遍 spaCy 解析**：路由调 `constituents` + `parse_deps` 各一次，
  而 `constituents` 内部又调一次 `parse_deps`。改成把 deps 传进去复用，
  实测 30 轮交替中位数 **16.8ms → 11.2ms，省 34%**。deconstruct 同样处理。
- **`DEP_LAS 89.87` 是错的**：那是 en_core_web_sm 旧版本的数，升到 3.8.0 后没跟着改，
  实测 `nlp.meta` 里是 **89.92**。改成 `dep_las()` 从模型 meta 读，三处硬编码去掉。
