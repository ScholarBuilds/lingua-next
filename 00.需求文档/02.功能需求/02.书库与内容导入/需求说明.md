# 书库与内容导入

## 1. 模块目标

内置公版书籍馆藏，支持导入书籍（epub/pdf/txt/md）与文章（粘贴/文件/URL），统一经服务端解析管线落库，为精读、点词、批注、进度提供稳定的定位锚点。

## 2. 归属模型（术语先定）

| 概念 | 含义 | 说明 |
| --- | --- | --- |
| 书库 | 内置公版馆藏 | 人人可浏览可试读（单用户场景即"未加书架也可读"） |
| 书架 | 用户选中的书与文章混排 | 引用表实现，移出书架不删正文/进度/批注 |
| 文章 | 用户导入的单篇内容 | 与书籍章节共用同一套解析与阅读能力 |

- 书架按"在读 / 未开始 / 已读完"分段展示，段内按最近打开倒序；书与文章同卡片、角标区分。
- 加入书架是显式动作；书库整本入架，单章不可入架。

## 3. 功能需求

### 3.1 导入

- FR-01 书籍导入：epub（主）、pdf（文本层）、txt/md；worker 异步解析，进度可见。
- FR-02 文章导入：粘贴文本/Markdown、文件、URL 抓取正文（服务端抓取 + 正文提取，失败可回退查看原始 HTML 快照）。
- FR-03 内置书目：首批 3-5 本公版书（Gutenberg 来源），含封面、章节目录、字数与预计时长。
- FR-04 超长内容提示实际字数并给"按章拆分/截断导入"显式选项，不静默截断；扫描版 PDF 提示暂不支持并保留原件。
- FR-05 导入失败保留原始输入与原件，可重试。

### 3.2 解析管线（服务端执行一次并落库）

```
归一化(编码/空白/连字符断词合并) → 章节/段落切分(保留标题层级、列表、引用、代码块)
→ 句子切分(spaCy, 处理缩写/小数/引号) → 词元标注(字符区间/原形/词性/可学习标记) → 落库
```

- FR-06 客户端不得自行重新分句；所有偏移以段落原文 UTF-16 码元为基准（与 JS 字符串口径一致）。
- FR-07 归一化不修正拼写与语法；代码块不参与词元标注与翻译；解析失败的段落单独标记并保留原文，不拖垮整篇。
- FR-08 短段落（诗歌、题词）不得静默丢弃；切章失败必须报告而非整本压成一章。

### 3.3 书库管理

- FR-09 封面：epub 内嵌封面抽取自托管；无封面时生成程序化封面（书名排版 + slug 确定性哈希取色，不用随机哈希）。封面叠加进度条，仅进度 > 0 显示。
- FR-10 书籍详情页：章节目录（章节名/字数/预计时长/已读态）、当前章高亮；分卷章节折叠显示。
- FR-11 书级进度 = 已读段落去重数 ÷ 段落总数，请求时聚合不落表；列表与详情共用同一进度口径。
- FR-12 文章库：按标题/来源/标签/状态/完成度筛选排序，全文检索（PostgreSQL FTS）；列表必须分页。
- FR-13 删除文章二次确认并说明连带范围（批注、进度同删；产生的生词默认保留）。

## 4. 业务规则

- BR-01 `段落ID + UTF-16 字符区间` 是全系统通用锚点：批注、词元命中、词组区间、生词出处、句级进度、朗读高亮全部依赖，任何改变偏移口径的决策需同步评估六处。
- BR-02 移出书架只删引用行；重新加入接着读。
- BR-03 目录不提供"手动标记整章已读"（会伪造段落级进度数据）。
- BR-04 阅读来路（书库/书架/文章）决定返回文案与落点，枚举唯一定义。
- BR-05 阅读计时只累计前台可见且有交互的时长，增量上报。

## 5. 实现方案

| 部件 | 方案 | 开源参考 |
| --- | --- | --- |
| epub 渲染（前端） | foliate-js（vendor 进仓库封装） | johnfactotum/foliate-js |
| epub 解析（服务端） | ebooklib + lxml 抽正文与封面 | aerkalov/ebooklib |
| PDF | pdf.js 渲染 + 文本层点词 | mozilla/pdf.js |
| URL 正文提取 | trafilatura（Python，正文提取业内基准） | adbar/trafilatura |
| 分句/词元 | **实际实现用 pysbd + 正则切词**（选型时写的 spaCy 从未引入，见下注） | pysbd/pySBD |
| 阅读器形态参考 | Readest、Lute v3 的文本/词汇状态模型 | readest/readest、LuteOrg/lute-v3 |
| 公版书源 | Project Gutenberg（epub 直下） | gutenberg.org |

> [!warning] 分句实现与本表原文不符（2026-08-19 核实）
>
> 本表原写「分句/词元用 spaCy en_core_web_sm」，但代码里 grep 不到任何 `spacy` import，
> 实际是 `domain/segmentation.py` 的 pysbd 分句 + 正则切词，`tokenize()` 只记 UTF-16 偏移，
> **没有语境词性标注**（词性来自 ECDICT 的统计分布字段 `pos`，如 `j:99/n:1`）。
> 模块 01 的 v2 文档还明确写过「不引入 spaCy 运行时」。
>
> 影响：[模块 14 语法学习](../14.语法学习与写作纠错/需求说明.md)要做依存句法可视化，
> **引入 spaCy 是新增依赖**，不是「已有但没用起来」。

> [!note] 渲染与解析双轨说明
>
> epub 前端用 foliate-js 原样渲染（排版还原好），服务端解析管线另存句子/词元表用于点读定位与分析缓存。两者通过"章节 + 段落序 + 字符区间 → CFI"映射表对齐，映射在解析入库时生成。这是本模块最关键的技术验证点，进 M1 垂直切片。

## 6. 数据要点

```
book(id, slug, title, author, cover_key, source: builtin|imported, file_key)
chapter(book_id, ordinal, title, is_section, article_id)
article(id, book_id?, title, source_kind: book|paste|file|url, source_url, raw_key)
paragraph(article_id, ordinal, text, kind: text|heading|code|quote)
sentence(paragraph_id, ordinal, char_start, char_end, content_hash)
token(paragraph_id, char_start, char_end, surface, lemma, pos, learnable)
shelf_item(kind: book|article, ref_id, added_at, last_opened_at)
reading_progress(article_id, last_paragraph, last_sentence, read_paragraphs, duration_s)
```

## 7. 验收要点

- AC-01 300 页 epub 从上传到可阅读 < 60s；同一文件两次导入切分结果一致（批注不漂移）。
- AC-02 前端渲染位置与服务端句子定位可互相映射（点击渲染文本能命中正确 sentence 记录）。
- AC-03 删除书籍时派生表清理完整，存在用户批注/进度时默认拒绝并报数，需显式确认。
- AC-04 URL 导入的文章记录来源网址与抓取时间，此后以落库正文为准不重新抓取。

## 8. v2 内置馆藏（2026-08-19）

原 FR-03 只要求「首批 3-5 本」，实际库里长期只有一本导入书。本版把内置馆藏做成
成规模、分难度、可检索的书库。

### 8.1 书目（FR-368）

40 本 Project Gutenberg 公版书，按 CEFR 梯度分三档：

| 档位 | 数量 | 定位 | 代表 |
| --- | --- | --- | --- |
| `starter` 入门 | 12 | A2-B1，童书与寓言，句子短、从句浅 | Alice、Oz、Peter Pan、伊索寓言、格林童话 |
| `core` 进阶 | 14 | B1-B2，通俗小说与冒险科幻，叙事线性 | 福尔摩斯、金银岛、野性的呼唤、时间机器、德古拉 |
| `deep` 精读 | 14 | B2-C1，文学经典与思想著作，长句与古体词多 | 简爱、白鲸、瓦尔登湖、沉思录、君主论 |

每本带：难度档、两个题材标签、一句话导读（说清"为什么值得读、难在哪"，
不写空泛推荐语）。清单在 `server/domain/builtin_books.py`。

### 8.2 ID 可信度（FR-369）

> [!warning] 外部资源 ID 不能凭记忆写
>
> CLAUDE.md 记着前车之鉴：首版 YouTube channel_id 凭记忆写了 5 个，3 个是 404。

- FR-369a 40 个 `pg_id` 全部用 Gutenberg 官方全量目录 `pg_catalog.csv` 现场核对标题与作者。
- FR-369b 清单里落值（Gutenberg ID 是永久标识），但 seed 脚本保留 `--verify` 模式
  随时重新拉目录复核，不匹配即报错退出。
- FR-369c 展示名与目录名不一致的作者用 `author_key` 显式声明（Sun Tzu ↔ Sunzi）。

首轮核对纠出两处凭常识会选错的：Robinson Crusoe 的 `min(id)` 命中的是
「单音节简写童书版」（6936），原著是 521；Moby Dick 取 2701 而非早期版 2489。

### 8.3 入库（FR-370）

```
seed_books.py → 下载 epub → 落 media_root → 建 Book(source=builtin) → 入队 parse_book
                                                                        ↓
                                          分章 → 分段 → 分句 → 词元标注（与导入书同一条管线）
```

- FR-370a 幂等：按 `external_id`（Gutenberg 电子书号）判定是否已入库，中断重跑只补缺的。
- FR-370b 支持 `--only <slug>` / `--difficulty <档>` / `--refresh` / `--verify`。
- FR-370c 下载内容做 epub 头校验（`PK` 魔数 + 最小体积），不是 epub 直接判失败不入库。

**实测**：40 本全部下载入队 0 失败，解析后 41 本 `ready`、1716 章、64188 段落。

### 8.4 书架呈现（FR-386）

- FR-386a 难度筛选条（全部/入门/进阶/精读）带各档数量；仅在有内置书时出现。
- FR-386b 封面左上角难度角标，三档三色；卡片下方两个题材标签，`title` 挂一句话导读。
- FR-386c 关键词同时搜标题、作者、题材标签、导读；与难度筛选是与关系。
  实测搜「科幻」精确命中 4 本（海底两万里 / 弗兰肯斯坦 / 世界大战 / 时间机器）。
- FR-386d 标签行留固定高度让卡片等高，否则栅格参差会把下一个分组标题顶得贴上来。

### 8.5 一条运维约束（BR-06）

> [!danger] `--reload` 不能监视 media 目录
>
> 40 本书让 `server/data/media` 涨到 2.4G，`uvicorn --reload` 默认监视整个 server 目录，
> watchfiles 被拖垮后 worker 子进程反复死掉——现象是 reloader 主进程还在、
> 端口还 LISTEN，但所有请求超时，看上去像"接口写挂了"。

起服务一律限定监视目录：

```bash
uv run uvicorn app.main:app --port 8100 --reload \
  --reload-dir app --reload-dir domain --reload-dir worker
```


### 8.6 封面（FR-387，2026-08-19）

> [!warning] 「没有真封面」是个误判
>
> 上一版结论是"Gutenberg 的 epub 大多不带内嵌封面，要真封面得另找图源"。查库发现
> **41 本的封面早就抽出来并落库了**，而且是高清扫描件（普遍 800px 以上，最大 1824x2726）。
> 书架显示程序化封面是因为 `cover_url` 返回 `/books/{id}/cover` 少了 `/api` 前缀，
> 请求打到 vite dev server 拿回 index.html，`<img>` 报错后回落程序化封面。
> 下判断前先查数据。

- FR-387a 封面 URL 带 `/api` 前缀（前端 `<img src>` 直接用它，不走 fetch 助手）。
- FR-387b 封面统一存 `.img`，扩展名不带类型信息，端点按文件头嗅探给真实 MIME
  （否则退化成 `application/octet-stream`）。
- FR-387c 封面 URL 带 `?v={mtime}` 版本参数并配一周强缓存：换了封面 URL 才变，
  用户立刻看到新图；没换则 URL 恒定，缓存照常命中。少了它换封面后看到的还是旧图。
- FR-387d 封面体检 `fetch_covers.py --audit`：尺寸门槛 + **下半部分最大单色占比**。
  Gutenberg 给没有历史书封的书塞的是自动生成的抽象图（下半整块纯色 + 几何形状 +
  Project Gutenberg 字样），实测 8 张生成图占比 58.5%-76.5%，33 张真封面最高 30.9%，
  阈值取 45%。
- FR-387e 不合格的从 Open Library 换：按书名+作者搜，书名主干须是候选标题的**开头**
  （只要求"按序出现"会放进 *The Lost Art of War* 冒充 *The Art of War*），
  排掉带斜杠的合订本，按版次数降序**逐个下载试到通过体检为止**（头名也可能是 128px 小图）。
- FR-387f 通行书名与 Gutenberg 全称不一致的书用 `search_title` 显式给出
  （*The Life and Adventures of Robinson Crusoe* 在 Open Library 上就叫 *Robinson Crusoe*）。

**实测**：8 本占位封面全部换成真实书封（伊索寓言龟兔赛跑插画、格林童话城堡油画、
秘密花园后印象派、海底两万里古海图、小妇人现代插画、鲁滨逊 Bantam Classic 版、
黑暗之心雨林绘画、孙子兵法红印章 + 古画战争场面），经看图核验 8/8 书名作者吻合、
无 Project Gutenberg 字样。全库 41 本封面体检 0 不合格。

> [!note] 色数不是判据
>
> 首版体检用"去重色数 < 2500"判生成图，把 4 本真封面误判了——格列佛游记是黑白铜版画，
> 256 色却货真价实。看图核验（并行 agent）纠出这个错，才换成纯色占比判据。

## 9. 媒体存储与出口（2026-08-19）

### 9.1 为什么现在不上对象存储

调研与实测结论，供将来重新评估时对照：

| 判据 | 事实 |
| --- | --- |
| 多进程共享 | api 与 worker 已用同一个 bind mount，需求本就不存在 |
| 性能 | 本机实测 372MB 整片 1.22s（318 MB/s）、Range seek 20.5ms；多一跳 HTTP 转发 +26% |
| 数据安全 | 2.33G 里不可再生的只有 0.2M（录音与导入原件），数据库真正的用户资产约 11M |
| MinIO 现状 | `minio/minio` 已于 2026-04-25 归档只读（核实 GitHub API `archived: true`），Docker Hub 镜像标 Archived、最新 tag 停在 2025-09-07；社区版控制台自 RELEASE.2025-05-24 起被降级为纯 object-browser |
| 单机成本 | MinIO 单节点预分配 1GiB 内存，与整个数据集同量级 |

自建对象存储对「迁移方便」**没有帮助**：数据仍在本机磁盘，换服务器一样要搬，
而且搬的是对象存储内部格式，还多出 access key 与 bucket policy 要迁。
真正做到「数据不用搬」的是云对象存储，那是另一个决策。

**重新评估的触发条件**：api 与 worker 拆到不同机器 / 数据超单盘容量 / 要 CDN 回源 /
要对外分享文件（预签名 URL）。

### 9.2 存储抽象（FR-388）

`domain/storage.py`：业务只认 key 不认路径，将来换后端只改 `get_storage()` 的分派。

- FR-388a `Storage` Protocol：`stat / exists / read / read_range / write / delete`
  加两个逃生口 `local_path()`、`presigned_url()`。
- FR-388b **不引入 fsspec**。它的同步 API 在 uvicorn 事件循环里调用不报错而是静默阻塞
  （守卫只在 fsspec 自己的循环里触发），表现为 QPS 无故塌陷；`s3fs.open_async()`
  读取不带 Range，视频拖进度条会每次重拉整片。PyFilesystem2 最后一次实质提交在 2022。
- FR-388c `safe_key()` 统一校验：key 多数来自数据库列，脏值不能变成任意文件读取。
  **语义**：`..` 段一律拒绝；前导斜杠归一化而非拒绝（剥掉后仍锁在 media_root 内，
  安全上没有缺口，而对脏数据更宽容）。
- FR-388d 写入走临时文件 + 同目录 rename，读方不会看到半截文件。

> [!note] 两个逃生口不能删
>
> `local_path()` —— Starlette 的 `FileResponse` 只接受本地路径，它的 Range 支持
> （206 / multipart / If-Range）全绑在这上面；worker 里 ffmpeg、yt-dlp 也只认路径。
> `presigned_url()` —— 将来换云存储时让浏览器直连，绕开应用转发这一跳。

### 9.3 X-Accel-Redirect（FR-389）

`app/media.py` 统一出口，开关是 `LINGUA_XACCEL_PREFIX`：

| 取值 | 行为 | 用在 |
| --- | --- | --- |
| 留空 | 应用自己发（`FileResponse`） | 本机开发，直连 8100 或走 vite 代理 |
| `/__media/` | 空响应 + `X-Accel-Redirect` 头，nginx 接管 | 生产（compose 已设） |

同一份路由代码两种部署都对，不必为环境写分支。

- FR-389a 收益：`FileResponse` 用 anyio 逐 64KB 读，372MB 要跳 5900 多次线程池，
  折算约 1.3 秒 CPU / GB 出流量，这些 CPU 直接从业务请求里抢。
- FR-389b 内部 URI 必须 percent-encode——nginx 收到后会 unescape 一次，
  漏编码时文件名里的空格、中文、`%`、`?`、`#` 会截断或指错文件。
- FR-389c 三类必须回落到应用直发：不在 media_root 下的（预览片段在
  `data/preview_cache`）、带 `BackgroundTask` 清理的（导出 apkg 用完即删，
  nginx 还没读完文件应用就删了）、未配前缀的。
- FR-389d 空壳响应**不要**带 `Accept-Ranges` / `ETag` / `Content-Length`：
  前两个会覆盖或被丢弃，最后一个 nginx 直接忽略，设了反而让人误判生效。
- FR-389e nginx 侧 `location /__media/` 必须带 `internal`，外部直访返回 404。
  该前缀不能落在 `location /api/` 之下，否则会被 proxy_pass 再转一圈。

### 9.4 顺带修掉的两处部署阻塞

都是既有问题，因为镜像自 2026-08-17 起没重建过所以一直没显形，
而部署到 Linux 服务器第一步就会撞上：

1. **`Dockerfile` 缺 `build-essential`**：`ctc-forced-aligner` 没有预编译 wheel，
   要现场编 C++ 扩展，缺编译器直接 `error: No such file or directory: 'g++'`。
   一并补上运行时要用的 `ffmpeg`（whisper 转写与预览裁切都依赖它）。
2. **`.dockerignore` 没排除 `data/`**：`COPY . .` 把 2.4G 媒体文件塞进构建上下文
   （实测 build context 传了 1.91GB 还没传完），既拖慢构建又胀镜像层——
   而这些文件运行时是由卷挂载进来的（`LINGUA_MEDIA_ROOT=/media`），
   本就不该进镜像。
