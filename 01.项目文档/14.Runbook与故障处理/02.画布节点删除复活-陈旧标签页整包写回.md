# 画布节点删除复活：陈旧标签页把旧文档整包写回

- 日期：2026-08-23
- 状态：服务端判据已落地并有用例守；**前端那一半未做**，单靠服务端关不掉（见「为什么服务端一个人修不完」）

## 现象

两个标签页 A、B 开着同一块画布：

1. A 里删掉节点 `ntest0` → 保存成功，服务端确实少了它，静置 20 秒不反弹
2. B 是陈旧的（手里那份还有 `ntest0`），在 B 里**只是拖动另一个不相干的节点**
3. `ntest0` 立刻回到服务端

## 根因

画布是**整包全量 PUT**（`PUT /studio/canvases/{id}`，body 带 `base_version` 做乐观锁），
409 时前端按 BR-145 做并集合并（`web/src/features/studio/canvasStore.ts` 的
`mergeAndResave` / `mergeDocs`，原话「宁可复活不丢结果」）。

在 B 看来，`ntest0` 是「我有、服务端没有」——这与「我刚新建的节点」**在载荷里长得
一模一样**（`mergeDocs` 的注释自己写明了这一点）。前端确实有删除墓碑
（`canvas-tombstones.ts`），但它是模块级内存变量，**只存在于执行删除的那个客户端**，
B 没有那条记录，于是把旧副本当新节点写了回去。

客户端自己解决不了，判据必须来自服务端。

## 服务端这一半（已落地）

`studio_canvas` 加一列 `deleted_nodes`：`{节点 id: 删除生效的 version}`
（迁移 `f2a9c47b1d63`）。

| 环节 | 位置 | 行为 |
| --- | --- | --- |
| 记删除 | `app/routers/studio.py::save_canvas` | 载荷里消失的节点 id 记在**这次保存后的新 version** 上 |
| 清记录 | `domain/studio.py::record_node_deletions` | 落库文档里还在的 id 一律不留记录（否则下一个更旧的客户端会把这个活节点再删一次） |
| 有界 | 同上 | 上限 500（= `MAX_NODES`，一次全选删的最大产出），满了扔版本最旧的 |
| 判据 | `domain/studio.py::nodes_deleted_after` | 记录版本 **>** 客户端 `base_version` → 是它读完画布之后才被删的，丢；**≤** → 客户端读到过删除之后的画布，同 id 节点是它重建的（⌘Z 走这条），留 |
| 交名单 | 409 响应的 `buried_nodes` | 按该客户端的 base_version 算出「你读完之后被删掉的」清单 |
| 交全量 | `GET` 详情的 `deleted_nodes` | 整份记录，供 SSE 帧到达后的本地合并使用 |

连线不用另记：丢掉的节点 id 不进 `normalize_canvas_payload` 的 `ids` 集合，指向它的边
被既有的悬空过滤一并带走。

## 为什么服务端一个人修不完

两条要同时成立的约束把服务端锁死了：

1. **乐观锁已经把 `base_version` 落后的保存全挡在 409 上**。所以「记录版本 > base_version」
   这个判据在**写路径上永远不会命中**（能写进去的保存必然 `base_version == 当前版本`，
   而记录版本不可能大于当前版本）。它真正决定结果的地方是 409 响应里那份名单。
2. **B 的复活发生在合并之后的那次重存**：前端 409 合并（或 SSE 帧到达后的合并）会把
   `base_version` 洗成服务端最新版本，再 PUT。那一刻，B 的请求与 A 按 ⌘Z 重建同 id
   节点的请求**逐字节一致**——都是「当前文档 + 这个节点」，`base_version` 都等于删除
   产生的那一版。服务端没有客户端身份，分不开。

把判据放宽成 `>=` 能挡住 B 的第一次重存，代价是 ⌘Z 撤销删除的那次保存被静默丢掉
（实测：`tests/test_studio.py::TestCanvasDeletionLog` 里把 `>` 改成 `>=`，
`test_recreated_node_is_not_blocked` 与 `test_undo_puts_the_same_node_id_back` 立刻转红）。
丢用户内容比复活更糟，所以判据保持 `>`。

## 前端那一半（待做，约 5 行）

服务端已经把名单交出去了，前端在**合并的那一刻**用它——那时手里的 `s.version`
还没被洗，正是判据要的 `base_version`：

1. `mergeAndResave`：拿到 409 body 的 `buried_nodes`（或 `remote.deleted_nodes` 里
   版本 > 合并前 `s.version` 的那些），合并前 `rememberNodes(tombstones, buried, Date.now())`。
2. `mergeRemoteCanvas`（SSE 帧到达后的合并）：同样处理，这条路不经过 409。
3. `mergeDocs` 的**第一个循环**要加一道：本地节点若已下葬且远端没有，跳过。
   现在的墓碑判定只写在「远端有、本地没有」那个循环里，而跨标签页的旧副本恰恰在本地。

做完之后，前端墓碑仍然是第一道防线（单客户端内有效），服务端记录是跨客户端的唯一真相。
