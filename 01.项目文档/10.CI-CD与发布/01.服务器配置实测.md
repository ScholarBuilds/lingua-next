# 服务器配置：实测数据与选型

测于 2026-08-30，本机 Apple M1 Max（10 核 / 48GB），容器为 `deploy/docker-compose.yml` 那一套。
**全部是量出来的，没有估算**；量法附在每一节里，可复跑。

## 一、静息占用（实测，容器已跑 2 天）

`docker stats --no-stream`：

| 容器 | 内存 |
| --- | ---: |
| postgres:16-alpine | 193 MB |
| lingua-next-api | 248 MB |
| lingua-next-worker | 152 MB |
| redis:7-alpine | 10 MB |
| admin-web / learner-web（nginx） | 9 MB × 2 |
| **合计** | **约 620 MB** |

这是「一个模型都没加载」的状态——容器里 `/root/.cache/huggingface` 实测只有 4KB，
说明这套部署从来没真跑过转写或对齐。下面几节才是真实天花板。

## 二、峰值：按模型逐个量

量法：`resource.getrusage(RUSAGE_SELF).ru_maxrss` 取峰值，`ps -o rss=` 取当前值。

| 阶段 | 峰值 RSS | 说明 |
| --- | ---: | --- |
| 裸 python | 15 MB | |
| + FastAPI 全量 import | **191 MB** | API 进程的真实起点 |
| + ffmpeg 转 opus（32 分钟视频） | 28 MB | 子进程管道，主进程几乎不涨 |
| + 火山 ASR 跑完一条 32 分钟视频 | **198 MB** | 上传 5.3MB opus，本地零模型 |
| + CTC 对齐模型加载 | **1482 MB** | MMS-300M ONNX |
| + 对齐一条 31 秒音频 | **2366 MB** | |
| + 对齐一条 **32 分钟**视频 | **4259 MB**（常驻 3566） | 424 cue / 4355 词，**耗时 1264 秒（21 分钟）** |
| whisper **small** 转写 31 秒 | 1118 MB（常驻 921） | Docker 默认就是这一档 |
| whisper **large-v3** 转写 31 秒 | 3190 MB（常驻 2636） | 仅本机 `.env` 用 |

> [!warning] 现在的内存天花板是 CTC 强制对齐，不是 whisper
>
> 对齐一条 32 分钟视频：**峰值 4259 MB、常驻 3566 MB、耗时 1264 秒（21 分钟）**。
> 单块音频已经限死 30 秒（`BLOCK_SPAN_S`），单次推理不可能要 4GB——
> `ctc_forced_aligner/__init__.py:671` 用**默认 SessionOptions** 建
> `onnxruntime.InferenceSession`，也就是开着 CPU arena 分配器（只涨不还）。
> 一度以为这就是主因，**实测证伪**——同一条视频关掉 arena 对照：
>
> | | 默认 arena | `enable_cpu_mem_arena=False` | 差 |
> | --- | ---: | ---: | ---: |
> | 峰值 RSS | 4259 MB | 3593 MB | −666 MB（−16%） |
> | 常驻 RSS | 3566 MB | 2823 MB | −743 MB（−21%） |
> | 耗时 | 1264 s | 1232 s | −32 s（**略快**，不是慢） |
>
> arena 只占 700MB，**配置档位不变**。剩下 3.6 GB 的出处：模型本身约 1.5 GB、
> 波形 123 MB，其余是 `ctc_forced_aligner` 拖进来的 torch/torchaudio 与通用分配器碎片，
> 都不归 onnxruntime 的 arena 管。
>
> 关 arena 仍值得做（白拿 700MB 且不慢反快），但它是省一档不是换一档。
>
> **时间上它同样是大头**：21 分钟 = 0.66× 实时，与 whisper large-v3 的 0.74× 同一量级。
> 换句话说 2026-08-30 那次改造把转写从 0.74× 降到 0.034×，
> 但整条管线的耗时只从约 45 分钟降到约 22 分钟——剩下的 95% 全在对齐上。

## 三、并发放大

`worker/main.py:266` 是 `max_jobs = 4`，四条视频管线在**同一个进程**里并发。
`domain/alignment.py` 的 `_lock` 只保护模型加载不保护推理，所以对齐会真的并行跑。
模型那 1.5GB 是共享的，其余按并发数放大。

小机器上把 `max_jobs` 调到 1 或 2 是最省事的降配手段。

## 四、配置建议

| 内存 | 能做什么 | 代价 |
| --- | --- | --- |
| **4 GB** | 够跑，但要 `max_jobs=1`，且尽量别导入 30 分钟以上的视频 | 长视频对齐时会贴着上限 |
| **8 GB**（推荐） | 一条长视频（4.1G）+ API 降级转写（1.1G）+ 基础（0.6G）≈ 5.8G，有余量 | |
| 16 GB | 可以并发导入多条视频 | 个人自用多半用不上 |

**CPU**：4 核起步。火山 ASR 是网络等待不吃 CPU；ffmpeg 转码 32 分钟视频 16 秒；
真正吃 CPU 的只剩 CTC 对齐（32 分钟视频 >13 分钟单线程）。

**磁盘**：镜像 3.34 GB + 模型卷约 1.7 GB（whisper small 464MB + MMS-300M 1.2GB，
首次调用时从 HuggingFace 下载，国内单线程约 1.3MB/s，见 CLAUDE.md）+ 媒体 2.8 GB（会长）
+ `data/` 1.2 GB + postgres。**起步 15 GB，媒体按每小时视频约 1GB 预留**。

## 五、2026-08-30 那次改造改善了什么

对比要分清「本机」和「Docker」，两边基线不同：

| | 本机（`.env` 指 large-v3） | Docker（compose 覆盖成 small） |
| --- | --- | --- |
| 改造前转写 | whisper large-v3，3.2 GB / 0.74× 实时 | whisper small，1.1 GB，准确率明显低（ADR-007） |
| 改造后转写 | 火山 API，**0 本地内存** / 0.034× 实时 | 同左 |
| 音素评分模型 | 1.5 GB 磁盘，本机加载 | 从未在容器里跑通过（缺 espeak-ng） |

所以：

- **本机**：转写这一环省掉 3.2 GB 与 96% 的时间，音素模型省 1.5 GB 磁盘。
- **Docker**：内存天花板本来就是 CTC 对齐，**没怎么降**；真正的收益是
  **质量上去了而内存没涨**——原先为省内存用的 small，现在换成了云端大模型
  （与 large-v3 词序列一致度 97.7%，还自带标点、零宽词跨度为 0）。
- 两边共有的改善：API 进程的降级路径从可能常驻 2.6 GB 降到 921 MB
  （`whisper_fallback_model` 钉死 small，见 `app/config.py`）。

## 六、还能再降的两条（都没做，需要拍板）

0. **关掉 onnxruntime 的 CPU arena**（见上表）：省 700MB、快 32 秒，
   代价是要 monkey-patch 第三方库的 session 构造（它不给传 SessionOptions 的口子）。
   不改架构不改行为，但也换不来更低的配置档位。

1. **视频管线不跑 CTC 对齐，直接用火山的词级时间戳。**
   省掉 1.2 GB 模型、约 4 GB 峰值、长视频 13 分钟 CPU，
   连带 `ctc-forced-aligner` 拖进来的 torch/onnxruntime（镜像依赖层 1.55 GB 的大头）。
   代价：词级时间戳从「CTC 声学标注」退到「绝对偏移中位 50ms，±100ms 内 79%」，
   卡拉OK 高亮会略松。反向的好处是零宽跨度从 5.4% 降到 0——那些本来就渲染不出来。
   **但跟读评测第 0 层的词级置信度只有 CTC 给得出**（火山的 `confidence` 字段实测恒为 0），
   要么保留对齐只服务跟读那条几秒的短音频路径（内存代价小两个数量级），
   要么那一项也一起放弃。

   > [!warning] 换之前必须先量「学习单元切得一样不一样」
   >
   > 词级时间戳不只喂卡拉OK。`domain/subtitle_sentences.py` 拿**词间静音**当切分判据：
   > `_find_hard_gap`（≥2.0s 硬切）、`_find_split`（≥0.30s 候选切点）、
   > `span_s`（单元 ≤7.0s）。一句话切成几个学习单元、切在哪，是这批时间戳算出来的。
   >
   > 火山的 50ms 中位偏移相对 300ms 阈值是 17%，理论上够，但**没有端到端实测**。
   > 该做的验证：同一条视频两套时间戳各跑一遍 `build_sentences`，
   > 比单元数、边界偏移、有没有出现半句单元。而且切分变了会触发
   > `study_unit_state` 的迁移逻辑，影响已有学习进度。

2. **Dockerfile 改多阶段构建。** `build-essential` 只在编 `ctc-forced-aligner` 的
   C++ 扩展时需要，现在留在最终镜像里（apt 那层 710 MB）。改多阶段能砍掉几百 MB。
   若采纳第 1 条不再需要 ctc-forced-aligner，这一层可以直接不装。

## 复跑方法

```bash
# 静息占用
docker stats --no-stream --format "{{.Name}}\t{{.MemUsage}}"

# 各模型峰值：把要量的调用塞进这个壳
cd server && uv run python -c "
import resource; rss=lambda: resource.getrusage(resource.RUSAGE_SELF).ru_maxrss/1048576
print(f'{rss():.0f} MB')
"

# 火山 vs 本地 whisper 的同素材对比
cd server && uv run python scripts/compare_asr.py 21 25 23 11 26 13 28 --json /tmp/asr.json
```
