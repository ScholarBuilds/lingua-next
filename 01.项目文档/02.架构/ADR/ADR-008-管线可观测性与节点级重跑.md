# ADR-008：管线可观测性自建 run/step 记录，不引入编排器

- 状态：accepted（2026-08-18 scholar 确认，故障驱动）
- 日期：2026-08-18
- 决策人：scholar

## 背景与约束

v5 上线后新入库的三条视频字幕列表全空。根因是 arq worker 为 8-17 18:19 起的进程，
内存里跑的是 ADR-007 三级管线并入 `ingest_video` 之前的代码：cue 正常写入
（12/26/9 条），句层从未构建，轨 meta 为空，中文轨缺失。**视频状态一路
`ready 100%`，故障静默六小时，最终靠手工查 SQL 才发现。**

真正的缺陷不是"忘了重启 worker"，而是：

1. 管线没有节点级记录——`video.status` 六个粗粒度值 + 单一 `progress` 数字，
   每步做了什么只在会滚掉的 worker 日志里；
2. `ready` 的判定只看流程跑完，不看产出质量，成了静默降级的放行者；
3. 没有版本指纹，代码更新后旧产物无从识别；
4. 重跑粒度只有整条 `retry`（重下载重转写）与 enrich 的 `only=`。

约束：个人项目单机部署（Compose 已有 postgres / redis / litellm / nginx 四个服务）；
scholar 要求业内最佳实践、能抄开源就抄、一劳永逸、不接受补丁式优化。

## 选项对比

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| A. 引入 Dagster | Run/Step 模型、步骤子集重跑、staleness 全都现成 | 需独立 server + 自己的 DB（第五、六个服务）；其重跑作用在"任务"上，我们要的"换 whisper 模型重切句层""让 AI 校验字幕"是领域动作它不提供；UI 是另一个 App，与产品割裂 |
| B. 引入 Prefect 3 | 可无服务器本地执行，接入成本比 Dagster 低 | **至今不能从 UI 重跑单个失败 task**（[discussion #15829](https://github.com/PrefectHQ/prefect/discussions/15829)），而节点级重跑正是本次的核心诉求；UI 同样割裂 |
| C. 自建 run/step 记录，抄它们的模型与语义 | 与领域动作天然贴合；UI 长在产品里；零新增服务；arq 不动 | 需自己实现记录与重跑编排（约 400 行领域代码） |

## 决策

**采纳 C：arq 保持不变只负责派活，运行记录由领域层落库，抄 Dagster 的数据模型与交互语义。**

这正是 arq 官方推荐的 `on_job_start` / `after_job_end` + 自建表模式——arq 本身不提供
步骤级introspection，其 job 状态是由 Redis 键的存在与否派生的，不适合承载领域语义。

具体抄什么：

| 借鉴 | 落到本项目 |
| --- | --- |
| Dagster Run / Step 模型 | `pipeline_run` / `pipeline_step` 两表 |
| Dagster 步骤子集重跑（step subset） | `scope = single \| downstream \| failed` |
| Dagster asset `code_version` staleness | `pipeline_step.code_version` + 陈旧标记与批量重跑 |
| Dagster [issue #32052](https://github.com/dagster-io/dagster/issues/32052)（重跑时改配置，官方尚未做） | `config_override` 直接做进重跑入口，并落 `step.config` 可回溯 |
| Airflow `TaskInstance.try_number` / Gantt | `pipeline_step.attempt` / 时间轴视图 |
| OpenTelemetry span 语义 | 字段命名对齐（status / attributes / 父子关系），将来接 APM 不必改模型 |
| React Flow + dagre（MIT） | DAG 可视化与自动布局，唯一新增前端依赖 |
| LLM-as-judge 无参考评测 | `domain/subtitle_review`：无金标准时用 LLM 裁判 + 确定性指标组合，不做 WER |

## 理由

**为什么不为了"抄开源"而硬塞编排器。** 项目原则是"能抄开源就抄开源、禁止重复造轮子"，
但这次要抄的是**设计**而不是**运行时**：Dagster 与 Prefect 解决的是"跨团队多 DAG 的调度与
血缘"，而这里是单一线性管线（12 节点、只有 enrich 分四叉）上的**领域级微调**——换 whisper
模型重切、让 LLM 复核断句、手工改一句后重算下游。这些没有任何编排器提供，装了编排器仍要
自己写，且额外多背两个服务和一套割裂的 UI。抄模型与语义、不抄运行时，才是这里成本最低
且不重复造轮子的解。

**为什么 `ready` 必须收紧。** 本次故障能静默六小时，直接放行者就是"流程跑完即 ready"。
新判据是「有 whisper 轨 + 句层非空 + 译文覆盖 100%」，不满足落 `degraded`。这条规则下
本次三条视频会立刻标黄。

**为什么要 `code_version`。** 这是本次故障的根本盲区——产物是哪版管线跑的，系统完全不知道。
Dagster 用 asset `code_version` 解决同一问题：上游代码版本变了，下游标 stale。照抄即可，
代价只是一个常量与一次比较。

## 影响

- 新增两表与一次迁移；`worker/tasks.py` 各步包一层 `step()` 上下文管理器。
- 视频状态机新增 `degraded`：前端视频库与追踪页需处理该态。
- 新增前端依赖 `@xyflow/react` + `dagre`（均 MIT）。
- `verify_video_pipeline.py` 的检查项提炼为 `domain/pipeline_health.py`，脚本改为调用它，
  避免两套标准。
- AI 校验每次入库自动跑一次，增加一次 LLM 调用（scholar 已确认接受）。
