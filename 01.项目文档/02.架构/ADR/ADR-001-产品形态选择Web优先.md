# ADR-001：产品形态选择 Web 优先 + 本地服务端，桌面壳后置

- 状态：accepted（2026-08-17 scholar 确认）
- 日期：2026-08-17
- 决策人：scholar

## 背景与约束

旧版是 macOS 原生客户端，重构版需要在 Web 端与 Electron 客户端之间做形态决策。产品四大主链路（词库背单词、书库精读点译、视频字幕学习、AI 实时语音对话）对平台能力的真实诉求：

| 能力诉求 | 浏览器可满足 | 说明 |
| --- | --- | --- |
| epub/pdf/txt 渲染与点词 | ✅ | foliate-js、epub.js、pdf.js 全部是浏览器技术 |
| 视频播放 + 字幕同步 + 点击跳转 | ✅ | `<video>` + WebVTT，asbplayer 已在浏览器验证过该形态 |
| 实时语音对话（低延迟、可打断） | ✅ | WebRTC / WebSocket，OpenAI Realtime 官方即走 WebRTC 进浏览器 |
| 录音、播放多音色 TTS | ✅ | MediaRecorder / Web Audio |
| YouTube 视频下载 | ❌ 浏览器不行 | 需要 yt-dlp，属于服务端能力 |
| ASR 字幕转写（whisper 系） | ❌ 浏览器不行 | GPU/CPU 密集，属于服务端能力 |
| 翻译/AI 结果持久化 | ❌ 纯前端不行 | 需要数据库，属于服务端能力 |
| 系统划词、全局快捷键、剪贴板监听 | 仅桌面壳可满足 | 旧版功能，新版已降为非目标 |

关键观察：所有"浏览器做不了的事"全部是**服务端能力**而不是**桌面壳能力**。产品本来就需要一个本地服务端（yt-dlp、whisper、数据库、翻译编排），Electron 唯一独占的系统级功能（划词取词）已被移出范围。

## 驱动因素

- 避免旧版教训重演：原生/客户端技术栈把 UI 迭代成本抬得过高。
- 开源复用最大化：目标参考项目（Lute v3、asbplayer、qwerty-learner、Readest）核心全是 Web 技术。
- 个人部署：本机 Docker Compose 一键启动，浏览器直接访问，无签名、公证、安装包负担。
- AI 协作开发效率：Web 前端 + API 服务端是 AI 代码生成成熟度最高的形态。

## 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| A. 纯 Electron 客户端（本地内嵌逻辑） | 单安装包；可做系统级功能 | 主进程塞 yt-dlp/whisper 编排复杂；升级分发麻烦；重蹈"客户端绑架架构"覆辙 |
| B. Web 优先（自托管 Web App + 本地服务端，Docker Compose 部署） | 服务端能力天然归位；前端纯 Web 可自由复用开源；零安装分发；未来加桌面壳/移动端只是加壳 | 无系统级能力（已非目标）；首次使用需起一次 Compose |
| C. Tauri/Electron 壳 + 本地服务端混合 | 有桌面入口感 | 首版多维护一层壳，收益只剩"独立窗口图标" |

## 决定

采用 **方案 B：Web 优先**。产品 = 浏览器前端 + 本地服务端（Docker Compose 编排多个服务）。桌面壳（Tauri 优先于 Electron，体积与内存占用更优）作为后续演进项，仅当出现真实的系统级需求（全局快捷键、系统划词回归）时再启动。

## 后果

- 前端一套代码通吃：本机浏览器、局域网其他设备、未来云服务器部署。
- 视频文件、书籍文件由服务端管理，前端通过流式接口访问，天然规避 Electron 文件路径耦合。
- 实时语音走浏览器 WebRTC，与 OpenAI Realtime 等云端方案的官方推荐路径一致。
- 放弃系统级划词取词等旧版 macOS 独占功能（已列入非目标）。
- 需要一份清晰的 `docker compose up -d` 启动文档作为"安装体验"。

- 验证：M1 里程碑用书库精读垂直切片验证浏览器内点词、TTS、翻译链路延迟达标。
- 复审：若 M2 结束时出现无法绕过的桌面独占需求，重开本 ADR。
