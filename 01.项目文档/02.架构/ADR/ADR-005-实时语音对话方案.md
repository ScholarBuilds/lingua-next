# ADR-005：实时语音对话采用"云端语音模型直连优先，自建管线为备选"双轨

- 状态：accepted（2026-08-17 scholar 确认）
- 日期：2026-08-17
- 决策人：scholar

## 背景与约束

需求 FACT：AI 实时语音对话对标 ChatGPT 语音模式——亚秒级首响、随时打断（barge-in）、口语陪练；AI 陪读要求模型持有整篇文章上下文，阅读中随口提问。延迟目标：用户停止说话到 AI 开始出声 < 1s（P50）。

实时语音的两条业内路线：

| 路线 | 原理 | 代表 |
| --- | --- | --- |
| 语音到语音（S2S）模型直连 | 单模型端到端处理音频，浏览器 WebRTC 直连供应商 | OpenAI Realtime API、Gemini Live API |
| 级联管线（VAD→ASR→LLM→TTS） | 自建各环节拼装，任意 LLM 可用 | pipecat、LiveKit Agents |

## 驱动因素

- 打断响应与首响延迟是产品硬指标，S2S 直连是当前业内延迟最优解，且浏览器端 WebRTC 由供应商官方支持。
- 自建管线的价值在供应商自由度（可换任意 LLM/TTS）与成本控制，但每一环的工程打磨（VAD 灵敏度、打断截断、回声）都费时。
- 个人项目应先用最短路径拿到能用的体验，再决定是否值得自建。

## 候选方案与决定

**双轨制，直连为主**：

1. **主路径：OpenAI Realtime API（WebRTC）**
   - 浏览器 `RTCPeerConnection` 直连 OpenAI；`api` 服务只负责签发 ephemeral token、下发会话配置（场景 prompt、语速、音色）、会后取回转写记录落库。
   - AI 陪读复用同一会话：建立会话时把当前文章全文 + 阅读位置注入 instructions/context，阅读器滚动时通过 data channel 增量同步位置。
2. **备选路径：pipecat 自建管线**（后置里程碑，仅当出现以下任一触发条件才立项）
   - Realtime API 成本超出个人预算红线；
   - 需要接入不提供 S2S 的国产模型做语音陪练；
   - 网络条件导致直连不可用。
   - 自建时组件基线：Silero VAD + faster-whisper（流式）+ LiteLLM 任意模型 + edge-tts/kokoro，WebRTC 侧用 LiveKit 或 pipecat 内建 SmallWebRTC。
3. 会话记录统一落库：无论哪条路径，转写文本、纠错反馈、生词都进学习资产模型，可回放复习。

## 后果

- M2 即可交付接近 ChatGPT 语音体验的陪练，无自建管线的调音周期。
- 语音对话供应商锁定 OpenAI（主路径），通过备选路径保留退出能力；两条路径共用会话记录模型，切换对数据层透明。
- 前端语音层按"信令/媒体/会话状态"分层封装，保证双轨可切换。

## 修订记录

**2026-08-17 修订 1（scholar 确认探测结果后生效）**：主路径变更为**火山引擎豆包端到端实时语音**（`wss://openspeech.bytedance.com/api/v3/realtime/dialogue`，Resource-Id `volc.speech.dialog`）。变更依据：
- scholar 现有火山凭证已实测开通（WebSocket 101 握手 + StartConnection→ConnectionStarted 协议层全通），零开通成本
- 国内直连免代理，消除原主路径（OpenAI Realtime）在大陆网络可用性与 API 计费账户两大前置风险
- 原生 S2S 可打断，同一凭证覆盖豆包 TTS 2.0（并入 TTS 高质量档，Resource-Id `seed-tts-2.0`，音色须用 uranus/saturn 系列）
- OpenAI Realtime 降为备选（官方 API Key 到位且需要 GPT 系语音时启用）；GLM-Realtime 次备选（¥0.18-0.3/分钟，需另开官方 Key）；回合制级联（whisper+LLM+edge-tts）保留为兜底与降级路径
- 集成注意：python websockets 16.0 解析该服务重复 server-timing 头会崩，用 websocket-client 或自处理握手；上行 PCM 16kHz int16，下行可要 PCM 24kHz float32

**2026-09-02 修订 2（CR-010 D-1 / D-2）**：贾维斯语音前台也走这条火山实时链路，但职责与陪练不同——

- 贾维斯模式下会话的对话模型不产生回答（550/559 丢弃），回答来自执行引擎；引擎输出分句后经 `500 ChatTTSText` 让**同一条会话**念出来（官方明说播报中被新 query 中断时无需再发 end 包，协议自带打断）；`450 ASRInfo` 是唯一的抢话信号，交给服务端 `VoiceOrchestrator`（`domain/jarvis_voice.py`）裁决——barge-in 只停播、steer 追加进在飞 turn、abort 才 `turn/interrupt`。
- **麦克风全程不关**。CR-009 D12「TTS 播放期间暂停麦克风上行」作废：那正是打断不了的根因。模块 07 BR-01「用户开口即打断、200ms 内停声」在贾维斯链路上按同一口径验收（`scripts/measure_voice_latency.py`）。
- `dialog.model` 现已必传（`LINGUA_VOLC_DIALOG_MODEL`，默认 1.2.1.1）；贾维斯的 `end_smooth_window_ms` 调到 500。
- 第二步迁「端到端实时语音-全双工」Seeduplex 3.0（`v3/duplex/realtime/dialogue`，model 1.2.6.1）：原生 function calling 把引擎注册成 `computer_task`，`response.cancel` 协议级打断，`speech_text_buffer.replacement` 指定念什么。供应商经 `VoiceProvider` 接缝可换，前端只认 `/jarvis/voice/ws` 的帧契约（CR-010 §3）。
- interpreter 内置的 `thread/realtime/*`（Codex 实时语音）与 OpenAI Realtime 仍是备选：握手写死 OpenAI 形状，接火山需要自研翻译层，只做探针不实施。

**2026-09-02 修订 3（CR-010 §6.8 真机验收）**：

- Seeduplex `output.format.type=pcm` 的实际下行按 24 kHz Float32 little-endian 处理；不得按 Int16 解码。WebSocket 只有收到带 `transport` 的 ready 状态后才允许开启麦克风。
- 上游握手采用有界重试；失败时本地能量 VAD 立即接管，Silero 后台加载，之后按退避周期探测上游并在静音窗口回切。本地模型冷启动不得阻塞 ready。
- 播放侧以本地连续 RMS 帧触发抢话，服务端先 flush 播放队列再等协议取消回执。真实设备停声 P50 123.95ms、P95 124.8ms；AEC direct / loopback 均回落到底噪且无误触发，ALWAYS-ON 采用全双工。
