# 模型命名与展示口径

> [!warning] 一句话规则
>
> **用的什么模型就显示什么模型。** UI 上凡是标着「模型」的位置，一律显示上游真实模型名
> （`gpt-image-2`、`deepseek-chat`），不许出现 `image-illustration` 这种能力 slug。

## 1. 两层名字

| 层 | 例 | 是什么 | 谁定的 |
| --- | --- | --- | --- |
| **能力名**（capability） | `translate-fast`、`repair-agent`、`image-free` | 业务代码唯一认得的路由键：一条业务链路要哪一类模型 | 代码里的常量（`domain/credentials.py` 的 `ALL_CAPABILITIES`） |
| **中文能力名**（label） | 快速翻译、修复代理、自由出图 | 能力名给人看的那一面 | `app/routers/config.py` 的 `CAPABILITY_META`，随 `/config/bindings` 每行返回 |
| **上游真实模型名**（model） | `gpt-image-2`、`deepseek-chat` | 这次调用真正发给上游的模型 | 模型部署行 `upstream_model_id`；上游回报了就以回报的为准 |

能力 → 部署由 `capability_binding` 决定，未绑定直接报错（核心原则 5）。**能力名不可删**：删了就没法给每条链路单独换模型，而那正是 `/settings/models` 存在的意义。

## 2. 各自出现在哪

| 场合 | 放什么 | 说明 |
| --- | --- | --- |
| 业务代码变量、参数、类型 | 能力名 | 标识符一律写 `capability`，不写 `alias` |
| 路由解析、绑定表、`/settings/models` | 能力名 + 中文能力名 | 配置态，用户在这里挑的是「哪条链路配哪个模型」 |
| 调用台账 `model_invocation` | `capability` 与 `model` 两列都有 | `model` 只放真名；唯一例外见 §5 |
| 产物落库（`analysis_result.model`、`image_asset.model_reported`） | 真实模型名 | 记的是「这份内容是谁产的」，填能力名等于伪造出处（核心原则 4） |
| UI 的「模型」位 | 真实模型名 | 见 §3 |
| UI 的「能力」位 | 中文能力名 | 不露 slug |

## 3. UI 显示口径

先问一句：**用户在这个位置想知道的是「这是哪个能力」还是「实际用了哪个模型」？**

| 位置 | 显示 | 例 |
| --- | --- | --- |
| 标着「模型」的字段、芯片、标题 | 真实模型名 | `gpt-image-2` |
| 能力选择器、绑定列表的能力列 | 中文能力名 | 插图 |
| 两个都要说清（换模型菜单、资产详情） | `<中文能力名> · <真实模型名>` | 修复代理 · deepseek-chat |
| 查不到真名（未绑定、还没发生调用） | 如实写「未绑定模型」 | 不拿能力名顶替 |

前端统一走 `web/src/lib/model-label.ts`：

- `modelText(model)` —— 「模型」位的文本，空值退化成 `未绑定模型`；
- `capabilityWithModel(中文能力名, 真名)` —— 唯一的 `A · B` 拼接口，别在组件里手写模板串。

已按此改造：`web/src/features/pipeline/RepairPanel.tsx`（头部「当前修复 Agent 模型」显示真名，能力写进 title；换模型菜单分「跟随能力绑定 / 指定这条部署」两组，前者标签是 `修复代理 · deepseek-chat`）。

## 4. 为什么不再说「别名」

`alias` 是 LiteLLM 时代的措辞：那时网关里注册的**真的是别名**，一个别名对应网关配置里的一条模型条目。LiteLLM 已于 2026-08-23 彻底删除，调用一律按 `capability_binding` 直连上游，网关这一层不存在了——留着「别名」只会让人以为「模型还有个小名」，进而心安理得地把 `image-free` 摆到「模型」位上。

所以：**代码里表示「能力」的标识符一律叫 `capability`**。真正的别名概念本项目目前没有；将来若真的出现（同一模型的多个称呼），必须叫 `model_alias` 并在注释里写清指的是模型的别名，不是能力。

## 5. 唯一允许把能力名写进 `model` 位的地方

路由解析失败时（能力没绑、插件没 Provider），这次调用**根本没有模型**可报。台账仍要留一行，此时：

- `plugin_id` 写 `unresolved`，明示这一行不是一次真实调用；
- `model` 位落能力名。

出处：`server/domain/llm.py:_prepare_route`、`server/app/routers/llm_admin.py:probe_route`。除此之外任何地方把能力名写进 `model` 都是 bug。

## 6. 遗留字段（名字还叫 alias，装的是能力名）

改名要动线上契约或数据库，未随本次一起改：

| 类型 | 位置 | 改名代价 |
| --- | --- | --- |
| DB 列 | `repair_session.model_alias`、`image_asset.alias`、`image_job.alias`（`domain/models.py`） | Alembic 迁移 + 全部读写点 |
| HTTP 字段 | `POST /llm/test` 的 `alias`；生图 `generate/edit/stream` 的 `alias`（form 与 JSON 两种形态）；`POST /repair/sessions` 的 `model_alias` | 前后端同步 |
| Python 公开签名 | `imagegen.render_images / edit_images / generate_for / ingest`、`image_stream.render_streaming` 的 `alias=` 关键字参数 | 路由器 / worker / 画布 / 测试同批改 |
| 前端类型 | `lib/api-image.ts`、`lib/api-studio.ts`、`lib/api-repair.ts` 的 `alias` / `model_alias` 字段与 `REPAIR_ALIASES` 常量 | 跟随 HTTP 字段一起 |

这些位置都已就地加注释说明「装的是能力名」。已完成改名的：`domain/llm.py` 全量、`domain/image_stream.py` 与 `domain/imagegen.py` 的内部实现、`app/routers/llm_admin.py` 的处理函数。
