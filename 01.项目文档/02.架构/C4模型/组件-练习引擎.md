# 组件：练习引擎（exercise）

[模块 13 音标](../../../00.需求文档/02.功能需求/13.音标与发音训练/需求说明.md)与
[模块 14 语法](../../../00.需求文档/02.功能需求/14.语法学习与写作纠错/需求说明.md)都要出题，
两边各写一套渲染与判分必然走形。这一层把「题目长什么样」「怎么判对错」「答错了说什么」拆开。

> [!note] 这一层是补进来的
>
> 两个模块的需求初稿里，题型是散落在各自章节里的（听辨题、看音标选词、结构化输入题…），
> 没有统一的题目模型。补这一层的直接触发是 Khan Academy Perseus 的包拆分方式，
> 以及 Oppia 把「答错」建模成「误区」而不是「不等于正确答案」。

## 1. 三层拆分（抄 Perseus）

[Khan/perseus](https://github.com/Khan/perseus)（MIT，TypeScript，★1584，2026-08-19 仍在推）
是 Khan Academy 线上在跑的习题系统，12 个包里有三个正好对应我们要的三件事：

| Perseus 包 | 它解决的问题 | 我们的对应 |
| --- | --- | --- |
| `perseus-core` | 题目 Schema + 版本兼容迁移 | 题目 JSON 的形状与升级路径 |
| `perseus-score` | **评分与 UI 分离**，单题评分 + 总分聚合 | 判分逻辑可单测、可回归 |
| Widget Registry | 注册新题型，渲染器与数据解耦 | 加题型不动核心 |

**要抄的是这个拆分本身**，不是引入 `@khanacademy/perseus` 包——它带着 KaTeX、
数学键盘、Storybook 编辑器一大套，我们只要三种朴素题型。

### 1.1 评分必须与渲染分离

这是这一层唯一的硬约束：

```
题目 JSON ──→ Widget 渲染（React）──→ 用户作答
                                        ↓
                                   作答数据
                                        ↓
                              score(题目, 作答) ← 纯函数，无 DOM 依赖
                                        ↓
                        { correct, 误区id?, 反馈, 得分 }
```

判分是纯函数才能单测。音标模块的听辨题、语法模块的句型转换题，判分逻辑都要能脱离浏览器跑。

### 1.2 题型清单

| widget | 用在 | 作答数据 |
| --- | --- | --- |
| `minimal-pair` | 音标听辨（FR-393） | 选中的词 |
| `audio-choice` | 听音选音标 | 选中的 IPA 串 |
| `phoneme-decode` | 看音标选词 / 看词选音标（FR-395） | 选项 id |
| `referential-input` | 语法指称型结构化输入（FR-404-1） | 选项 id |
| `sentence-transform` | 句型转换 | 文本 |
| `error-correction` | 找错并改正 | 文本 + 选区 |
| `word-order` | 词块排序 | 顺序数组 |
| `speech-recording` | 跟读提交 | 录音 blob |
| `pronunciation-timeline` | 逐音素结果展示（只读） | — |

前七种判分是确定性的，进 FSRS；后两种走模块 09 与 13 的评测链路，不进 SRS（BR-94）。

## 2. 误区模型（抄 Oppia）

[oppia/oppia](https://github.com/oppia/oppia)（Apache-2.0，★6771，2026-08-19 仍在推）
的教育领域模型把「答错」建模成**可命名的具体误区**，而不是「不等于正确答案」：

```
答案规则  →  命中某个 misconception  →  定向反馈  →  跳转补救内容  →  再练对应题
```

举例（语法模块的真实场景）：

| 环节 | 内容 |
| --- | --- |
| 技能 | 一般过去时否定句 |
| 学习者答案 | `He didn't went there.` |
| **误区** | `didn't` 之后仍用过去式 |
| 定向反馈 | 时态已经由 did 承担，后面的动词恢复原形 go |
| 补救 | 助动词与实义动词的时态分工 |

这比「LLM 看一眼整句写段评语」适合做正式学习系统——**误区是有限的、可枚举的、可统计的**，
能回答「你这个错误犯过 5 次」和「这类错误该补哪一课」，LLM 的自由文本回答不了。

- 常见误区在出题时预先绑定（题目 JSON 里挂 `misconceptions: [{pattern, id, feedback, remedial_point_id}]`）。
- 没命中任何预设误区时才降级到 LLM 自由讲解。
- 语法模块的误区 id 与 ERRANT 的 55 类错误标签双向映射（FR-402）。

> [!tip] 同类设计的另一个参考
>
> [h5p-advanced-blanks](https://github.com/sr258/h5p-advanced-blanks) 把「具体错误答案」绑定
> 「具体反馈」并高亮提示词，是同一思路的轻量实现，填空题可直接照它的数据形状。

## 3. 内容生产管线

44 个音位、499 条语法点、每个点 2-3 道题——内容量不小且要能改。
[LibreLingo](https://github.com/kantord/LibreLingo) 的管线形状值得抄：

```
YAML 源文件（人写、可 diff、可 review）
   ↓  Schema 校验（失败即报错，不进库）
Python 编译器
   ↓  快照测试（内容改动可见）
前端 JSON（运行时只读）
```

- 内容用 YAML 写而不是直接塞数据库：可以进 git、可以 diff、可以在 PR 里 review。
- 编译期做 Schema 校验，把「音位卡片少了例词」这类错误挡在上线前。
- 快照测试让内容改动在 diff 里可见。

> [!warning] LibreLingo 已归档
>
> 2026-06-19 归档（★2631，AGPL-3.0）。**只抄管线形状，不引代码**——
> 管线思路不会因为归档而失效，但不要指望它有维护。

## 5. 明确不做

| 不做 | 理由 |
| --- | --- |
| 引入 `@khanacademy/perseus` npm 包 | 带 KaTeX + 数学键盘 + 完整编辑器，我们只要三类朴素题型。抄拆分方式不抄依赖 |
| 接 Oppia 平台 | 它是完整的教学平台（Python + Angular），只抄领域模型 |
| 引入 H5P / Lumi | 题型多但代码质量不统一，且 Lumi 会多出一个 Node sidecar |
| 抄 [OLI Torus](https://github.com/Simon-Initiative/oli-torus) 的实现 | Elixir 写的（★119，MIT），技术栈不通。它的 Activity/Part/Attempt/评分状态/内容版本**概念模型**可以参考，代码不行 |
| 自建题目编辑器 | 内容走 YAML + git，不需要可视化编辑器 |

### 6.1 实现里与设计不同的两处

**注册表在服务端不在前端。** 设计文档写「Widget Registry」时没有明确它在哪一侧。
实际把注册表放在 `domain/exercise.py`：题型的 `required` 字段与 `schedulable` 属性
都是**出题期与调度期**要用的，放前端等于让浏览器决定「这题进不进 FSRS」。
前端 `Widgets.tsx` 只有一张渲染分发表，不含任何判分或调度语义。

**「答错了说什么」也在服务端。** 判分结果里带 `misconception`、`feedback`
与正确答案（`detail.answer`）。前端拿到什么显示什么，不自己判断谁是正确答案——
这样「评分与渲染分离」才是真的分离，而不只是文件分开放。
